## Problem statement

Stand up the persistence foundation: Flyway migration infrastructure, the PostgreSQL 16 schema per DatabasePlan, and — the crux — the **Row-Level Security tenancy mechanism** (`tenant_id` + forced RLS + transaction-scoped `SET LOCAL app.tenant_id`) proven to structurally block cross-tenant reads. This is the #1 technical risk (RLS correctness) and the prerequisite for every tenant-scoped feature.

## Change class

CC-4 (schema/migration). Gates: G1, G2, G3 (RLS isolation suite), **G4 (R-DBA — expand–contract, forward-only, RLS integrity)**, G7, G8.

## Acceptance criteria (from DatabasePlan §14, scoped to Phase-0 baseline)

1. `V1__baseline.sql` creates the §2 schemas and tables per §3 conventions; Flyway applies cleanly on empty PG16 (as `eip_migrator`).
2. All tenant-scoped tables have RLS **enabled + forced**; a cross-tenant smoke test returns **zero rows** under the `eip_app` role (`NOBYPASSRLS`).
3. The `SET LOCAL app.tenant_id` mechanism (transaction-scoped; unset GUC errors, never silently returns zero rows) is implemented in `eip-tenancy` and covered by tests.
4. Scale-out invariants (DatabasePlan §15) hold: every unique constraint on tenant-owned tables includes `tenant_id`; no DB-global sequences on tenant-owned rows (UUIDv7 app-side).
5. `vector` extension installed; snake_case/singular conventions, `created_at`/`updated_at` touch trigger, enums as text+CHECK.

## Incremental delivery (this task, in order)

Because `V1__baseline.sql` is the *full* Phase-0 schema (DatabasePlan §7) and is a large, security-critical migration, it is built in reviewed increments on this branch (V1 stays a single growing file — nothing is deployed/applied to a durable environment until push, so V1 immutability is not yet engaged):

- **Increment 1 (this commit) — RLS foundation + tenancy core:** build wiring (Flyway/Postgres/JDBC/Testcontainers), the `core` schema + tenancy-core tables (`core.tenant` platform + `core.organization`, `core.business_unit`, `core.team`, `core.role`, `core.member`, `core.member_identity`, `core.secret`), the `R__rls_policies.sql` template, the `SET LOCAL` tenant-context mechanism, and a **Testcontainers RLS isolation test** proving TENANT_A/TENANT_B isolation. De-risks the crux.
- **Increment 2+ (continued):** remaining `core`/`audit`/`staging` infra tables (`external_ref`, `entity_link`, `connector`, `event_outbox`, `processed_events`, `audit_event` hash chain, …), the canonical schema stubs (`work`/`scm`/`cicd`/`quality`/`ops`), partition templates, pgvector RAG tables, the app roles, keyset-pagination + upsert verifications, and the schema-lint for §15 invariants.

## DoD evidence

*(filled per increment; Increment 1 below)*

- **RLS foundation (AC-2/AC-3):** `V1__baseline.sql` + `R__rls_policies.sql` enable+**force** RLS with the `tenant_isolation` policy (`USING`/`WITH CHECK` on `tenant_id = current_setting('app.tenant_id')::uuid`, no GUC default). The `TenantContext` + `SET LOCAL app.tenant_id` mechanism in `eip-tenancy` is proven by a Testcontainers pgvector-PG16 test connecting as the non-superuser `eip_app` (`NOBYPASSRLS`): TENANT_A writes an org; under TENANT_B context the read returns **zero rows**; a write under the wrong tenant is rejected by `WITH CHECK`; an unset GUC **errors** (never silent-empty).
- **Conventions (AC-5):** snake_case singular tables, UUIDv7 PKs (app-side; `gen_random_uuid()` safety-net default), `created_at`/`updated_at` + `core.tg_touch_updated_at()` trigger, enums text+CHECK, `vector` extension.
- **Scale-out invariants (AC-4):** unique constraints include `tenant_id`; no DB-global sequences on tenant-owned rows.
