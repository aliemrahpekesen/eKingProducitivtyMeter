**Fail-open/fail-closed matrix verification.** AP-6 (ArchitecturePrinciples) is the governing rule — "fail open on degradation, fail closed on security" — and the readiness policy (ObservabilityModel §9) is consistent with it: DB/migrations fail-closed (shed), Kafka/Redis fail-open (degraded-not-unready). DataFlow §8 audit rules (mutations fail-closed, read-audits fail-open-with-detection) are coherent but the read-audit exception sits in tension with AP-6's "never fail open: … security" list — it is a deliberate, bounded exception that should be recorded as such in AP-6 itself (FMA-10). There is, however, **no single consolidated matrix**: the behavior is scattered across DeploymentModel §9 (10 rows, no detection/runbook/RPO columns), DataFlow per-flow notes, ObservabilityModel §9, and AP-6 — and the scattered set misses the OTel Collector, Prometheus/Alertmanager, outbox relay, webhook buffer, and full-Kafka-outage (as distinct from broker loss) rows entirely (FMA-07).

## 3. Strengths

- **The architecture is failure-mode-literate at its core.** At-least-once + idempotent consumers + `eventId` dedup + transactional outbox (DataFlow invariants, EventModel §9) means worker crash, rebalance, replay, scale-out, and failover are all the *same* solved problem. This is the single most important property and it is consistently applied.
- **Readiness/liveness policy is exactly right** (ObservabilityModel §9): a Postgres outage sheds traffic without restarts; a Kafka blip cannot take down the API tier. Acceptance criteria §11 test it explicitly.
- **Connector failure handling is the best-documented area**: checkpoint resume, circuit breakers, DEGRADED states, schema-drift detection, poison-record skip-window with data-quality flag, feedback throttling of sync intervals under lag (DataFlow §1–§3, OperationsGuide §9 T2). Genuinely solid — nothing to add.
- **LLM/AI degradation is principled**: fallback chains, budget caps, score-only display, "citations unavailable" notices, S3-by-design severity (DataFlow §5–§7, OperationsGuide §13.1, MCPArchitecture degradation principle).
- **DR discipline is real**: tested-restore policy ("a backup that has not been restore-tested is treated as nonexistent"), distinct quarterly failover and restore drills timed against distinct RTOs (OperationsGuide §6.3); RPO/RTO numbers are consistent between DeploymentModel §9 and OperationsGuide §6.3, including the honest single-node relaxation.
- **DLQ operations are complete**: per-group DLQs, failure-metadata headers, inspect/classify/replay procedure, audited deletion, daily ageing report (EventModel §10, OperationsGuide §3.1, §10).
- **Kafka payloads deliberately not backed up** with a correct justification (canonical state in Postgres, re-sync from sources) — a mature choice most teams get wrong in both directions.

## 4. Weaknesses

- **Detection lags design.** The failure *behaviors* are mostly specified, but ~8 of the 19 failure modes above have no Prometheus rule in the shipped catalog (Postgres down, Kafka down/URP, disk pressure, Redis down, MinIO, Keycloak, cert expiry, outbox stall, webhook buffer growth). The project's own G6 rule — "a failure mode without an alert fails G6" (ObservabilityRequirements §6) — is violated by the architecture documents themselves.
- **The outbox relay is the platform's most under-observed critical component**: single publication path for every event (EventModel §9), yet invisible in the ObservabilityModel catalog, dashboards, alerts, and runbooks.
- **Unbounded accumulation states**: `outbox_events` during Kafka outage and `webhook_intake_buffer` during the same have no size bounds, no backpressure trigger, no overflow policy (DataFlow §3; EventModel §9/§11).
- **Freshness SLIs trust source clocks.** `occurredAt` is the source system's clock (EventModel envelope schema); no clamping, skew detection, or per-source exclusion is defined — one misconfigured tool corrupts an NFR-012 SLO.
- **Agent-run crash semantics unspecified** (rerun cost accounting, orphaned RUNNING rows, stale worker heartbeats).
- **Runbook anchors referenced by every alert do not exist** in OperationsGuide (shared finding with the Observability review, OBS-01) — in an incident, the paging alert's runbook link 404s.

## 5. Contradictions

1. **Audit retention:** DataFlow §9 and ObservabilityModel §2 say `audit_log` = **25 months minimum** (compliance-driven, configurable upward only); OperationsGuide §8 says "audit store retention is a compliance setting (**default 400 days**)". 400 days < 25 months — a compliance-relevant conflict.
2. **Raw staging retention:** DataFlow §9 says 90 days default (NFR-070, "long enough to re-normalize after mapper fixes"); OperationsGuide §10 housekeeping purges normalized `raw_*` rows "past the reprocessing window (**default 30 days**)". The re-normalization safety window is silently cut to a third.
3. **Artifact retention:** DataFlow §9 says generated artifacts = **24 months** (configurable per tenant); OperationsGuide §10 artifact-retention job deletes at "**default 180 days** unless pinned".
4. **Alert naming and DLQ thresholds** differ across ObservabilityModel §7, OperationsGuide §4, and EventModel §10 (documented fully in ObservabilityReview §5 items 1–2; the FMA consequence is that during an incident the runbook table and the firing alert cannot be matched by name).
5. **Failure-mode table vs infra reality:** DeploymentModel §2–§4 diagrams show a single OTel Collector while KubernetesOpenShift.md specifies a 2-replica gateway Deployment (a decision note) — the HA property of the telemetry path exists only in the infra doc, not in the deployment/HA source of record (§9 has no Collector row).

## 6. Missing decisions

An implementer will be forced to decide ad hoc:

- Maximum tolerated Kafka outage: outbox/webhook-buffer growth bounds, the backpressure trigger (pause sync staging at N rows?), overflow behavior on the intake path (503 vs unbounded growth), and drain rate/ordering after recovery.
- Raw blob (MinIO) write failure during sync: fail the batch, park, or skip-with-flag.
- Agent-run redelivery semantics: is a rerun a new `agent_runs` row or a resume; how token budgets account for crashed attempts; who reaps orphaned RUNNING rows and after how long.
- Read-replica staleness policy for dashboard queries under replication lag.
- Negative/absurd `occurredAt` lag handling in freshness SLIs (clamp, drop, flag per source).
- Whether webhook-configured connectors must also run periodic reconciliation polls (DataFlow §3 assumes convergence "with a later incremental sync" but never requires one to be scheduled).
- Kafka-down detection signal (broker `up` absence vs consumer-side error rate) and which alert inhibits the resulting lag/DLQ storm.
- Cert-expiry metric source in Compose topology (no cert-manager).
- Behavior of `EipScheduledJobFailed` coverage for jobs outside its enumerated list (audit archival, vector maintenance, DLQ ageing report — OperationsGuide §10 lists seven jobs; the alert names three).

## 7. Risks

### Operational
- **Silent-freeze risk (highest):** outbox relay stall or slow-burn Kafka degradation freezes analytics freshness with zero shipped alert; dashboards keep serving last state (by design), so users see plausible-but-stale data until someone notices manually.
- Dead runbook anchors + three alert taxonomies degrade time-to-mitigate in the first real S1.
- Retention contradictions (§5 items 1–3) mean a housekeeping job may destroy data the architecture promises to keep — raw re-normalization window and artifacts are the concrete casualties; audit is protected only if SecurityModel §7 actually governs the implemented config default.

### Data consistency
- Core replay/idempotency model is sound. Residual: DLQ 30-day expiry as silent loss path if the daily ageing report is ignored; `processed_events` 35 d > domain retention 30 d invariant holds ✓ (DataFlow §9 — previously broken, now fixed per DocumentationQualityReview #15).

### Scalability
- At 10× event rate, a multi-hour Kafka outage turns the outbox/buffer tables into Postgres-bloat incidents (millions of rows, vacuum pressure) — precisely when the platform is already degraded. Bounds must exist before the committed envelope is real, not at 10×.

### Security
- Fail-closed discipline is well specified (audit-coupled mutations, RLS erroring on unset GUC, webhook signature rejection). The read-audit fail-open exception needs to be *named* as an AP-6 exception so future implementers don't generalize it.
- T6 (suspected RLS misconfiguration → fail closed, suspend, probe, re-verify) is an unusually good runbook — keep it inviolable.

### Tenant isolation
- Tenant decommission (OperationsGuide §3.4) correctly lets Kafka key-space age out via retention; no gaps found beyond those already covered by the security review's scope.

### Implementation
- Phase 0/1 teams will wire alerts and runbooks per G6 against contradictory sources; every hour spent reconciling docs post-implementation is more expensive than fixing them now.

## 9. Area verdict & conditions

**Verdict: READY WITH CONDITIONS.** Mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items.

The failure-handling *design* is strong — idempotency-everywhere, outbox, correct probe/fail-open policy, principled AI degradation, real DR drills. What's missing is the *detection and bounding* layer: roughly eight failure modes have no shipped alert, the single most critical internal component (outbox relay) is invisible in the source-of-record observability docs, the Kafka-outage buffers are unbounded on paper, and three retention numbers contradict across documents in ways a housekeeping job would turn into real data loss. All are document fixes; none require redesign.

## 10. Inviolable principles

1. **Fail open on degradation, fail closed on security (AP-6).** A failing connector, saturated LLM, lost cache, or lagging consumer never takes down the API or dashboards; authentication, authorization, tenant scoping (RLS errors on unset GUC), webhook signature verification, and audit-coupled mutations never "temporarily allow".
2. **Readiness = PostgreSQL + Flyway, nothing else.** Kafka and Redis are degraded-not-unready; liveness never inspects dependencies. No new hard readiness dependency, ever.
3. **All event publication goes through the transactional outbox; all consumers are idempotent (dedup on `eventId`).** No dual writes, no fire-and-forget publish. This is what makes crash, replay, rebalance, scale-out, and DLQ replay uniformly safe — any code path that bypasses it breaks every failure-mode guarantee at once.
4. **An unaudited mutation cannot commit.** Audit writes share the mutating transaction; audit-write failure aborts the action. The only fail-open audit path is the named read-audit exception, bounded and loss-alarmed.
5. **Every failure mode ships its detection**: alert rule + runbook anchor + observable degradation state in the same change (G6). A failure mode without an alert is unfinished, including in architecture documents.
6. **A backup that has not been restore-tested is nonexistent.** Quarterly restore drill (≤ 4 h) and, on HA, quarterly failover drill (≤ 30 min) with zero acknowledged-event loss; RPO ≤ 15 min for production (NFR-021).
7. **Suspected tenant-isolation failure is S1 and fails closed** (OperationsGuide §9 T6): suspend/stop first, investigate second, re-verify with the isolation suites before re-enabling.
8. **Dedup-ledger retention strictly exceeds the longest replayable topic retention** (`processed_events` 35 d > 30 d domain topics + DLQ) — shrinking either side reopens the double-processing hole.
