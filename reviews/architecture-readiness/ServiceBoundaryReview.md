## 2. Extreme-scenario assessment

Calibration: committed envelope is PRD §6 / ArchitectureOverview D3 (≥10k repos, ≥1M WorkItems, ≥50 tenants, 100k events/h + 3× burst, ~5,000 engineers). Extreme scenarios are ~10× that.

| Scenario | Holds / Degrades / Breaks | Reasoning (cited) | Mitigation path |
|---|---|---|---|
| 500+ teams / 10,000+ users | **Holds** | API tier is stateless and horizontally scaled (ArchitectureOverview §8); read load hits pre-aggregated read models, "scales with users, not with ingestion volume" (§8); RBAC permission sets cached 5 min (§6.5). | None needed. Dashboard MV refresh cadence (DatabasePlan §8) is user-count-independent. |
| 100,000+ repositories (10× committed) | **Degrades** | ExternalRef upsert is a single unique-index probe (DatabasePlan §4) — write path holds. But `eip.domain.scm` has 12 partitions (EventModel §3) capping consumer parallelism at 12, and "changing partition count reshuffles keys… changed only with a drain-and-cutover runbook" (EventModel §7). Single Postgres writer absorbs all canonical upserts (ADR-003). | Credible, not foreclosed: over-provision partitions up front, drain-and-cutover runbook exists (EventModel §7); worker replicas scale to partition count (§8). Ceiling documented in SBR-13. |
| 10,000,000+ Jira issues | **Degrades gracefully** | work_item at 10M rows ≈ 20 GB (DatabasePlan §9 row sizes) — fine with the §4 index set. `work_item_transition` partitioning is explicitly deferred "until > ~200M rows" (DatabasePlan §6) — at 10× this triggers early. Backfill of 10M issues through one connector instance is paced by the per-instance rate limiter and 2h full-sync TimeLimiter (BackendPlan §7) — full syncs are resumable per stream/page-window (DataFlow Flow A). | Pre-activate transition partitioning at install-size detection; per-stream checkpoints already make giant backfills resumable. No boundary change needed. |
| 1,000,000+ deployments | **Holds** | cicd.deployment is a slim row (DatabasePlan §9: build/deployment ~500 B); DORA aggregation reads `ops.metric_value` by PK with partition pruning (DatabasePlan §4). | None needed. |
| 1,000+ K8s namespaces polled by one connector | **Degrades** | Bulkhead caps 10 concurrent calls per connector instance (BackendPlan §7); 1,000 namespaces through one instance serializes behind the semaphore and the 2h sync TimeLimiter. Sync leases are per-instance (ComponentModel §4 SyncScheduler). | Operators split into multiple connector instances (per-cluster/namespace-group) — supported since instances are the unit of config, rate limit, and checkpointing (ConnectorFramework via ComponentModel §3). Should be stated as the documented pattern. |
| 100+ configured integrations | **Holds** | 500 tool instances is inside the committed envelope (D3); topics are per connector *type*, not instance (EventModel §3), so topic count stays bounded; per-instance Redis-backed rate limiters shared between app and workers (BackendPlan §7). | None needed. |
| Very large Confluence/wiki spaces (100M+ RAG chunks) | **Degrades → SPI escape hatch** | pgvector default sized for 10M chunks (D3, ADR-005: "SPI keeps a high-scale escape hatch (10M+ chunks)"); HNSW build memory constraints acknowledged (DatabasePlan §11). At 10×, HNSW on one PG instance breaks. | Qdrant via VectorStore SPI is a real, contract-preserving path (ADR-005; DatabasePlan §11 keeps the relational chunk model unchanged with vectors in Qdrant). Genuinely solid. |
| High-volume metrics/logs/traces intake | **Holds by design** | EIP stores *references*, never raw log/trace bodies (DomainModel §9: LogReference "EIP stores references, never raw log bodies"); OTLP intake normalizes to canonical entities. The boundary decision to not be an observability store is the correct cut. | None needed; ops normalizer debounce for alert storms (EventModel §7). |
| Many tenants (500 at 10×) | **Degrades** | RLS is row-level, not instance-level (ADR-004) — tenant count doesn't multiply operational units. Kafka keys spread tenants across partitions (§6.1); "hot tenants are contained to their key range and can be throttled per-tenant" (§8). But one shared PG instance and one shared outbox serialize all tenants' writes. | Multiple EIP installations (the model is "50 tenants per installation", D3) — sharding by installation is the documented scale-out. Not foreclosed. |
| Sustained 1M events/h (10× committed) | **Degrades, first crack = outbox relay + single PG writer** | ALL publications flow through `core.event_outbox` via a poller that BackendPlan §8 defines as a *non-concurrent* Quartz job ("OutboxPollJob (short interval, non-concurrent)"). At committed load (28/s, burst 84/s) a single relay holds. At 10× (280/s sustained, 840/s burst) a single-threaded relay doing insert→publish(acks=all)→delete triples write amplification on the hottest table and becomes the throughput ceiling. EventModel §9 defines per-key ordering from "publishing outbox rows in insertion order per key" but no sharded-relay design exists. | Not foreclosed: relay can shard by partition-key hash (each shard preserves per-key order). Must be designed before it's needed — SBR-08. Compounded by the direct-produce-vs-outbox contradiction (SBR-04): if raw events bypass the outbox (per DataFlow A/C), the ceiling moves; the docs currently say both. |

Two deployables + self-hostable infra (§2.1). Genuinely the strongest part of the architecture. | None needed. |

## 3. Strengths

1. **The dependency rules are enforceable, not aspirational.** ArchitectureOverview §5 rules 1–6 + ComponentModel §10 matrix are backed by Spring Modulith verification for compile-time edges and ArchUnit for topic consumption (ArchitectureOverview §11 "Evolvability (D8)"), and AP-1 makes any new edge a CC-1 gated change. Few designs of this maturity make boundary violations a *build failure* before a line of code exists.
2. **No dependency cycles — verified, including via events.** I specifically probed the analytics→ai→analytics loop: `eip-ai` consumes `eip.analytics.metrics` and calls `MetricQueryService` (ComponentModel §10), but nothing `eip-ai` produces is consumed by `eip-analytics` (ComponentModel §11). The event-flow direction matches the compile-time direction. The declared matrix is acyclic. (The reports↔ai edge is a different story — see Contradictions #4.)
3. **ArchitectureOverview §5 and ComponentModel §10 are mutually consistent.** The "May depend on" column and the api/evt matrix align cell-for-cell, including the subtle "events-only" edges. Cross-document drift was clearly guarded here.
4. **The Python AI worker seam is a real extraction proof.** Attaching optional Python workers exclusively at `eip.ai.jobs`/`eip.ai.results` (ArchitectureOverview §2.2.4, §10) forces the AI job contract to be process-neutral from day one — the cheapest possible insurance on ADR-001's extraction promise.
5. **Cross-schema FK ban supports extraction.** DatabasePlan §1: FKs enforced only inside a schema; cross-context references are plain UUIDs validated at the application layer (DomainModel §14 rule 6). This is the single most important physical-design decision for later service extraction, and it is made correctly and consistently.
6. **Governance has teeth where it's wired.** CODEOWNERS coverage CI check + orphaned-code rule (ModuleOwnership §6), MODULE.md charters with owned tables/topics as L2 context (§3), docs-lint verifying §1-vs-CODEOWNERS drift (§7). AP-1/AP-3/AP-7 each name the gate that catches their violation.
7. **The event-sourcing stance is decisively non-event-sourced** (EventModel §11): PostgreSQL is the record, topic retention makes hidden replay-dependence structurally impossible. This closes off a whole class of boundary rot.

## 4. Weaknesses

1. **DatabasePlan §2 breaks the "every table has exactly one owning module" rule at its root.** The `core` schema mixes tables from four modules: `tenant/member/role` (eip-tenancy), `connector`, `connector_checkpoint` (eip-connectors/eip-ingestion per ComponentModel §3/§4), `external_ref` (eip-ingestion per ComponentModel §4), `event_outbox` (written by every module), `processed_events` (eip-workers per ComponentModel §9), `worker_heartbeat`. Schema-level ownership ("Owner module" column) is therefore fictional for `core`. The extraction path (§2.2.3 "split its schema into a dedicated database") cannot execute against a schema owned by four modules.
2. **eip-analytics owns no schema.** ComponentModel §5 says eip-analytics owns `metric_facts`, `rm_*`, `metric_definitions`, `risk_assessments`, `analytics_watermarks`. None of these appear in DatabasePlan §2; the closest artifacts (`ops.metric`, `ops.metric_value`) sit in the `ops` schema owned by "eip-core (operations)", and the dashboard MVs sit in the `reports` schema (DatabasePlan §8) owned by eip-reports. The module doing the platform's core computation has no physical home, and its read models live in another module's schema.
3. **eip-core is assigned five schemas it is forbidden to own.** ComponentModel §1: eip-core has "no persistence… Data owned: none (types only)". DatabasePlan §2 assigns `work`, `scm`, `cicd`, `quality`, `ops` to "eip-core (work mgmt)" etc. Meanwhile ComponentModel §4 gives *write* ownership of canonical entity tables to eip-ingestion. Three documents, three owners for the canonical model.
4. **The analytics read-path quietly authorizes cross-module SQL.** BackendPlan §5: "`JdbcClient` owns the analytics read side… metric rollups, DORA aggregations, risk-score scans **over `raw_*` JSONB and canonical tables**." `raw_*` is eip-ingestion's `staging` schema (DatabasePlan §2); canonical tables are eip-ingestion write-owned (ComponentModel §4). This directly violates ArchitectureOverview §5 rule 3 (no module accesses another's tables) and rule 4 (analytics consumes `eip.domain.*` only). EventModel §11 doubles down: rebuild "from (a) canonical tables — the normal path for full recomputation". Either the rule or the plan is wrong; an implementer will pick whichever unblocks them, and the ArchUnit tests will be written to match whichever doc they read first.
5. **Derived fields force an undeclared analytics→canonical write path.** DomainModel §14 rule 5: "Derived fields (`blocked`, `durationSeconds`, `causedIncident`, `readinessScore`, `Risk.score`) are recomputed by `eip-analytics` consumers, never written by connectors." Those columns live on `work.work_item` and `cicd.deployment` (DatabasePlan §3) — canonical tables that eip-analytics may not touch. No API, event, or ownership carve-out exists for this write-back. This is not a nit: `blocked` and `caused_incident` drive core metrics, and the write mechanism decides whether analytics can ever be extracted.
6. **The single Flyway history contradicts the extraction claim.** ArchitectureOverview §2.2.2: "Each module owns its schema (separate Flyway history per logical schema area)." DatabasePlan §7 and ModuleOwnership §1: one migration directory under `eip-app`, one baseline containing everything, gate-owned by R-DBA. The workers-extraction seam is *not* clean on the schema axis today, and no split plan exists.
7. **Topic ownership is one-producer in spirit but not in the catalog.** EventModel §3 lists multi-module producers without naming an owner: `eip.reports.jobs` produced by "API layer, schedulers, Report Composition agent" (the latter lives in eip-ai — a producer edge absent from ComponentModel §11); `eip.ai.jobs` produced by eip-app, eip-ai, and schedulers. MODULE.md charters will require "owned topics" (ModuleOwnership §3) but no document says which module owns which topic contract.
8. **Consumer-side governance has phantom consumers.** BackendPlan §9.1 lists "dashboard cache warmers" (module unstated) and an "`eip-app` SSE bridge" consuming `eip.ai.results` — but ComponentModel §11 says eip-app consumes nothing and ArchitectureOverview §10 says "`eip-workers` owns all Kafka consumption". It also lists `eip.reports.triggers` consuming `eip.domain.*` and `eip.analytics.metrics`, edges that ComponentModel §10 marks forbidden (eip-reports row: no evt edge to ingestion or analytics). The ArchUnit topic-consumption tests — the enforcement mechanism AP-1 relies on — cannot be authored against two contradictory matrices.
9. **Co-ownership defeats scoped G4 authority at the enforcement layer.** ModuleOwnership §2 defines scoped co-owner approval ("required only when the diff touches their scoped concern") but §4 note 1 concedes GitHub semantics: "any listed owner's approval satisfies the code-owner requirement; the co-ownership scoping of §2 is enforced by review convention." For `/backend/eip-analytics` (`@eip/r-da @eip/r-ba`), R-BA alone can merge a metric-semantics change that §1 says R-DA owns. The mechanism is weaker than the policy it claims to enforce.
10. **Read-model naming/placement drift.** ArchitectureOverview §8 and ComponentModel §5: `rm_*` tables. DatabasePlan §8 and AP-7: `ops.metric_value` + `reports.mv_*` materialized views. An implementer cannot tell which is authoritative, and the staleness contracts differ (see Contradictions #6).

## 5. Contradictions

Each contradiction cites both sides.

1. **Canonical-table ownership (three-way).** ComponentModel §1 ("eip-core… Data owned: none") vs DatabasePlan §2 (`work`/`scm`/`cicd`/`quality`/`ops` owned by "eip-core (…)") vs ComponentModel §4 (eip-ingestion owns "canonical entity tables (write ownership)"). Also DomainModel §4 says Product/Project/Roadmap/Initiative are "Owned by `eip-tenancy`" while DatabasePlan §2 puts `product`, `project`, `roadmap`, `initiative` in the `work` schema.
2. **Analytics data access.** ArchitectureOverview §5 rules 3–4 ("eip-analytics never calls eip-connectors or eip-ingestion — it consumes `eip.domain.*` topics only"; "No module accesses another module's tables") vs BackendPlan §5 (analytics JdbcClient scans "over `raw_*` JSONB and canonical tables") and EventModel §11 (rebuild from "canonical tables — the normal path").
3. **Publishing rule: outbox-only vs direct produce.** EventModel §9 ("no producer (normalizer, metric engine, sync run, or webhook handler) ever publishes to Kafka directly") vs DataFlow Flow A (`RSW->>K: produce eip.raw.jira` directly), Flow C (`WC->>K: produce eip.raw.github`, 202 fast, with `webhook_intake_buffer` only for Kafka outages) and ArchitectureOverview §4 (`Rel(app, kafka, "Publishes jobs/commands; outbox relay")`). This decides whether the outbox must be sized for raw-event volume and whether the 60s p95 webhook-freshness budget (CLAUDE.md key budgets) is achievable through a ~1s poller (BackendPlan §6).
4. **Who runs the outbox relay.** ComponentModel §8: OutboxRelay is a "shared component, active in both runtimes for their own writes" vs BackendPlan §8: the poller is a Quartz `OutboxPollJob` and "Quartz runs only in worker processes… never in the API app". If workers are down, ArchitectureOverview §9's Kafka-outage recovery ("outbox relay drains on reconnect") has no defined runner for eip-app's writes.
5. **Topic consumer matrix.** ComponentModel §10/§11 (eip-app consumes nothing; eip-reports consumes only `eip.reports.jobs` + `eip.ai.results`; eip-ai produces only `eip.ai.jobs`/`eip.ai.results`) and ArchitectureOverview §10 ("eip-workers owns all Kafka consumption") vs BackendPlan §9.1 (eip-app SSE bridge consumes `eip.ai.results`; `eip.reports.triggers` consumes `eip.domain.*` and `eip.analytics.metrics`; "dashboard cache warmers" consume `eip.analytics.metrics`) and EventModel §3 (Report Composition agent — eip-ai — produces `eip.reports.jobs`; "AI agents" consume `eip.analytics.metrics` ✓ consistent, but "report engine" consumes `eip.domain.workitem` per its Consumers column — also outside ComponentModel §10). Consumer-group naming also drifts: `eip.reports.render` (BackendPlan §9.1) vs `eip.reports.job-runner` (ComponentModel §7, EventModel §8); `eip.ai.executor` (BackendPlan §9.1) vs `eip.ai.orchestrator` DLQ (ComponentModel §6).
6. **Read-model freshness.** ArchitectureOverview §11 Scale scenario: "p95 event-to-read-model freshness stays ≤ 30 s" vs DatabasePlan §8: materialized views refresh "on a schedule (5–15 min per view)" and EventModel §12: domain→analytics lag SLO "p95 < 5 min". The 30s criterion is untestable as written unless it is scoped to the `metric_value` path only — no document says so.
7. **Flyway histories.** ArchitectureOverview §2.2.2 ("separate Flyway history per logical schema area") vs DatabasePlan §7 (single directory `backend/eip-app/src/main/resources/db/migration`, single baseline) and ModuleOwnership §1 (that one path, gate-owned by R-DBA).
8. **`processed_events` ownership.** ComponentModel §9 (eip-workers "Data owned: `processed_events`") vs DatabasePlan §2 (`core.processed_events`, `core` owned by "eip-tenancy / eip-core"). Note eip-workers is a composition root with "no business logic of its own" (ComponentModel §9) — a composition root owning a table is itself a boundary smell.
9. **Table-name vocabularies.** DatabasePlan §1 mandates singular (`work_item`); ComponentModel §§2–7 and DataFlow use plurals (`work_items`, `connector_instances`, `checkpoints`, `outbox_events` vs DatabasePlan `core.event_outbox`; `agent_steps`, `llm_providers`, `rag_index_state`, `report_jobs`, `report_subscriptions` have no DatabasePlan §2 home at all; `staging.webhook_intake_buffer` from ComponentModel §4 is missing from DatabasePlan §2's staging schema list).

## 6. Missing decisions

An implementer will be forced to decide these ad hoc:

1. **The write API for derived fields** (`blocked`, `causedIncident`, `readinessScore`) — event back through ingestion? An exported ingestion interface? Analytics-owned side table? (Weakness #5.)
2. **Single writer for `Risk`.** DomainModel §5 says the Delivery Risk agent (eip-ai) "writes AGENT-raised rows" into the Risk register (work context) while ComponentModel §5 has analytics "emit Risk entities" into `risk_assessments`. Two modules, one concept, no declared writer or API.
3. **Which module owns each topic contract** (owner column in EventModel §3) and the procedure for adding a subscriber (is a new consumer group on an existing topic CC-1? AP-1 covers *dependency* edges; subscription governance is implied but nowhere stated as the owner's consent).
4. **Which module hosts the dashboard cache warmer** consuming `eip.analytics.metrics` (BackendPlan §9.1) and how `eip-app` learns of AI job completion if it may not consume Kafka (SSE bridge vs polling `agent_runs`).
5. **The Flyway split plan at extraction time** — which V-history lines move with a module, how `core.event_outbox`/`processed_events` are replicated per service.
6. **JPA entity placement for canonical tables** — entities in eip-core (BackendPlan §1 says canonical entities live in eip-core) but repositories in eip-ingestion? Nothing states which module holds the `@Entity` mappings and whether other modules may map the same tables read-only.
7. **The documented pattern for scaling a single connector across huge estates** (1,000 namespaces / 100k repos): multiple instances per source vs streams-within-instance.
8. **Governance check for table ownership**: docs-lint verifies ModuleOwnership §1 vs CODEOWNERS (§7), but nothing machine-checks MODULE.md "Owned tables" against DatabasePlan §2 — the exact drift this review found would survive every existing gate.

## 7. Risks

### Scalability
- **Outbox relay as the first crack.** Single non-concurrent poller (BackendPlan §8) serializing all publications; fine at committed 28/s, strained at 10× 280/s with 3× bursts. No sharded-relay design. (SBR-08)
- **Single Postgres writer.** All canonical upserts + outbox + read models on one instance; read replicas deferred to Phase 5 (ArchitectureOverview §8). Documented ceiling; extraction path exists but only if SBR-01/02/06 restore schema ownership. (SBR-12)
- **Fixed partition counts** with drain-and-cutover as the only resize path (EventModel §7). (SBR-13)

### Data consistency
- Derived-field write-back (Weakness #5) risks two writers on canonical rows (normalizer upsert vs analytics recompute) with no declared conflict rule — last-write-wins on `work_item.blocked` across two consumer groups with independent lag.
- Read-model rebuild depends on 30d topic retention (EventModel §3) + canonical recompute; if analytics is denied canonical SQL (rule 4), rebuild beyond 30 days is impossible — AP-7's "rebuildable" guarantee silently narrows.

### Operational
- Relay-runner ambiguity (Contradiction #4): during a workers outage, eip-app writes accumulate in the outbox with no publisher; ArchitectureOverview §9 does not list "workers down" as a failure mode with a degradation contract for eip-app-originated events.

### Tenant isolation
- Boundary-adjacent only: shared `core.event_outbox` and `core.processed_events` are tenant-scoped with RLS (DatabasePlan §2 notes) — sound. No isolation findings in this area; isolation review is another board seat.

### Implementation
- The ArchUnit topic-consumption suite — the enforcement backbone of AP-1 — cannot be written until Contradiction #5 is resolved; whichever doc the first implementer encodes becomes de-facto law.
- Co-ownership any-of semantics (Weakness #9) means G4 authority on eip-analytics, eip-ingestion, eip-reports is ambiguous exactly where boundary disputes will occur.

## 9. Area verdict & conditions

**Verdict: READY WITH CONDITIONS.** Mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items.

The logical boundary design — 9 modules, the api/evt dependency matrix, build-failing enforcement, the events-only async spine, the Python-worker extraction proof, and the no-cross-schema-FK physical rule — is genuinely strong and I found no compile-time or event-flow cycle in the declared matrix. The 9-module cut is the right cut for this product and team topology. What is **not** ready is ownership ground truth: the documents disagree about who owns the canonical tables, the analytics data surface, the read models, the outbox path, and the topic consumer matrix. These are exactly the facts the ArchUnit/Modulith enforcement suite, the Flyway V1 baseline, and every MODULE.md must be written from — so they must be settled before any implementation task starts.

**Conditions gating readiness (must land in the source documents first):** SBR-01, SBR-02, SBR-03, SBR-04, SBR-05.

SBR-06…SBR-11 are due before Sprint 3; SBR-12/SBR-13 are consciously accepted ceilings to be recorded verbatim.

## 10. Inviolable principles

Implementation must never violate these, regardless of schedule pressure:

1. **One table, one owning module, one writer.** Every table appears in exactly one module's MODULE.md; cross-module data access is via the owner's exported `api` interface, Kafka events, or (post-SBR-02, if adopted) an explicitly enumerated read-only canonical grant — never ad-hoc cross-schema SQL, never a second writer. (AP-1; ArchitectureOverview §5 rule 3.)
2. **One topic, one owning module.** Every `eip.*` topic has a single contract owner; producing to or consuming from a topic outside the declared matrix is a build failure and a CC-1 change, never a code-review nit. (AP-1, AP-3.)
3. **Composition roots stay empty.** `eip-app` and `eip-workers` contain no business logic and own no domain tables; anything they "need" belongs in a domain module. (ArchitectureOverview §5; ComponentModel §§8–9.)
4. **eip-core stays a leaf and stays thin.** No persistence, no Spring business beans, no table ownership in the shared kernel — a fat kernel is the death of the extraction path. (ComponentModel §1; ModuleOwnership §2.3.)
5. **The async boundary is events-only.** No synchronous call path from `eip-app` into `eip-workers`, ever; the two deployables share a database and a broker, never a request path. (ArchitectureOverview §10.)
6. **Canonical model is authoritative; read models are disposable.** No fact lives only in a read model; every read model states its owner, refresh mechanism, and staleness contract, surfaced as `computedAt`. (AP-7; ADR-011.)
7. **No cross-schema foreign keys.** Cross-context references are plain UUIDs validated at the application layer. (DatabasePlan §1; DomainModel §14 rule 6.)
8. **Every message carries tenant scope in its key** per EventModel §7, and every consumer establishes the RLS binding from the envelope before any table access. (AP-2.)
9. **Boundary changes are governed, not discovered.** Any new dependency edge, topic subscription, or table-ownership move updates ArchitectureOverview §5 / ComponentModel §10 / DatabasePlan §2 in the same PR under G4 — the matrix in the docs and the matrix in the ArchUnit tests are the same artifact. (AP-1, AP-4.)
10. **The extraction seam is preserved continuously**: no shared transactions across module schemas, no new tables in shared grab-bag schemas, and every new integration point must answer "what happens to this edge when the module becomes a service?" in its design note. (ArchitectureOverview §2.2; D8.)
