## 2. Extreme-scenario assessment

Calibration: committed envelope is PRD §6 / ArchitectureOverview D3 (≥10k repos, ≥1M WorkItems, ≥50 tenants, 100k events/h, ~5,000 active engineers). Extreme scenarios are ~10× that.

## 3. Strengths

- **Cancellation semantics are better specified than most shipping products.** AgentArchitecture §2.2 defines cooperative cancellation with a persisted flag, checkpoint-observation points, idempotent cancel of terminal runs, audited cancel requests, discarded staged artifacts, a terminal `status=cancelled` envelope for parents/pollers, and an explicit disambiguation of validation-retry vs run-level retry. The acceptance criterion (§12) makes it testable.
- **Budget vs SLO separation is explicit and correct.** §3.3 and §10.1 state that budgets are hard stops above the p95 SLOs and that alerting keys on NFR-013, not budget breaches — a conflation most designs get wrong.
- **Context-window management fails loud.** §3.4's deterministic compaction with persisted step summaries and `BUDGET_EXCEEDED(CONTEXT)` instead of silently dropping mandatory evidence is exactly right, and compaction events are auditable.
- **Tenant isolation on shared inference (§7.1)** covers KV-cache/prefix-cache/speculative-decoding cross-request leakage with tenant-partitioned keys and a refuse-to-route rule, backed by a CI scenario — rare rigor.
- **LLM response cache design (§10)** keys on `principalGrantHash` + template version + exact prompt hash, restricts eligibility to deterministic calls, and keeps audit completeness on cache hits.
- **Degradation without LLM (§13)** genuinely makes AI additive (principle §1.2), with per-capability behavior including RFC 7807 `llm-unavailable` and audited skipped schedules.
- **Compose reserve (§6.1)** — child exhaustion never draining the compose reserve or sibling partitions is a well-thought-out starvation guard (the deadlock in AIR-02 is at the concurrency layer, not the budget layer).
- **Prompt governance (§8)**: versioned templates, per-run `(templateKey, version)` recording, tenant-override shadowing with upgrade flags, and eval-gated promotion.
- **Governance actually reaches this area.** CC-5 in QualityGatePolicy (R-AIA sign-off, eval subset at G2) plus AIValidationWorkflow §6's hard bars and the explicit "the non-blocking local-model job MUST NOT be cited as merge evidence" rule show the gates were designed by someone who understands eval theater.

## 4. Weaknesses

- **W1 — Kafka consumption model for long runs is unspecified.** AgentArchitecture §3.1/§2.2 (worker claims run from `eip.ai.jobs`) never states offset-commit timing, poll-loop decoupling, or `max.poll.interval.ms` posture, while §3.3 permits 60-min runs. See scenario row 1. This is the single most implementation-blocking gap in the AI runtime.
- **W2 — Queue-hold vs partition ordering.** §10: a run for a tenant at its `maxConcurrentRuns` cap "stays queued until a slot frees". On a Kafka partition this means either head-of-line blocking (one capped tenant stalls every tenant sharing the partition — a tenant-isolation violation in the QoS sense) or out-of-order skip-and-requeue, which needs a mechanism (delay topic, DB-backed dispatch) that no document names.
- **W3 — Fan-out deadlock** (§6.1 + §10), see scenario row 2.
- **W4 — Provider capabilities are declared at the wrong granularity.** §7.1 puts `Set<LlmCapability>` on `LlmProvider` while a single Ollama/vLLM endpoint serves models with divergent tool-calling, structured-output, and context-window support. §7.2's promise that "capability mismatches are excluded at resolution time, not discovered at call time" is unimplementable without per-`ModelDescriptor` capabilities. The SPI is published and semver'd (NFR-060), so shipping the wrong shape is expensive to unwind.
- **W5 — Token accounting is asserted, not specified.** §3.3 enforces `maxTokensTotal` "before each LLM call" — that requires a pre-call prompt-token estimate, and no tokenizer strategy exists for arbitrary local models. §11 stores `promptTokens/completionTokens` per call, but usage extraction differs by provider (Ollama `prompt_eval_count`/`eval_count`; OpenAI-compatible streaming requires `stream_options.include_usage`; abandoned streams may report nothing). §2.2 says abandoned in-flight calls are "still audited" — with which token/cost numbers is undefined.
- **W6 — Cost budgets are inert in the flagship deployment mode.** §7.1 (`pricePer1kTokens` 0 for local) + §10 means `maxCost` and cost ceilings never bind air-gapped/local-only — the platform's stated default (§1.1). The docs never say so, and admins will configure cost quotas that do nothing.
- **W7 — No minimum-model capability matrix** for the 18 agents; NFR-013's "reference hardware" is an open question (PRD §11 #8). Local-LLM-only feasibility per agent is an unwritten assumption.
- **W8 — Mid-generation fallback is undefined.** §7.2 advances the fallback chain "on provider error/timeout" but says nothing about failure mid-stream after partial output reached an SSE consumer (Configuration Assistant, dashboard explain): splice, restart, or surface?
- **W9 — Cancellation loose ends.** §2.2 does not state that terminal transitions release the Redis concurrency slot and the Redisson runId lock; does not define cancel propagation from a Report Composition parent to in-flight children (children share the parent's wall clock but hold their own slots); and the cancel-latency bound (one full LLM/tool call, since checkpoints are between steps) is implicit rather than documented.
- **W10 — Prompt-template ↔ model compatibility has no migration story.** §8 versions templates; §9 gates template changes through evals; AIValidationWorkflow §6 gates repo-side routing changes. But a tenant admin changing routing at runtime (§7.2, admin UI) puts never-evaluated (template, model) pairs into production with no eval smoke, no warning, no audit distinction.
- **W11 — AI-worker autoscaling on consumer lag** (DeploymentModel §6, KEDA on `eip_kafka_consumer_lag`) is a poor signal for long-running jobs and, pre-AIR-01, actively harmful (scale event → rebalance → interrupted runs).

## 5. Contradictions

1. **Gating evals: pinned local model vs no-real-LLM rule.** AgentArchitecture §9: "Regression evals per agent: run in CI against a pinned local model…" vs TestingStrategy §1 ("No test may call a real SaaS API or a real LLM"), §14 (AI evals PR stage = "schema/fake-LLM subset"), and AIValidationWorkflow §6 ("No real LLM anywhere in gating tests"; the local-model job "MUST NOT be cited as merge evidence"). One of these is wrong; the TestingStrategy/EOS position is the enforceable one (air-gapped CI, ≤20-min PR budget), so AgentArchitecture §9 must be corrected. Consequence to acknowledge honestly: with `FakeLlmProvider`, the "hard bars" (structure 100%, citation 100%, numeric fidelity 100%, grounding 100%) verify harness and guardrail plumbing, not model behavior — see AIR-08.
2. **Concurrency cap vs composition liveness.** AgentArchitecture §10 ("child runs count against the cap like any other run", claim-time gating) contradicts §6.1's implicit liveness assumption that spawned children eventually run while the parent is executing. As written the two sections deadlock each other at low caps (W3/AIR-02).
3. **AI worker HPA vs run continuity.** DeploymentModel §6 (autoscale `ai` workers on Kafka lag) is in tension with AgentArchitecture §3.1/§3.3 (long-running consumer-hosted runs): every scale event rebalances the group and interrupts runs. Resumability (§3.2) makes it survivable, not free — each interruption re-executes from the last checkpoint and re-runs LLM calls (cost + latency). Resolved by the same decision as AIR-01, plus AIR-11's scaling-signal note.
4. **Minor:** Validation Agent budget "charged to the parent run" (§5.16) vs §6.1's per-section budget partitions — for a composed report it is ambiguous whether a section's validation pass draws from the child partition or the 20% compose reserve. Folded into AIR-02's target text.

## 6. Missing decisions

An implementer will be forced to decide ad hoc:

1. Offset-commit timing and poll-loop decoupling for `eip.ai.jobs` consumers; `max.poll.interval.ms` posture (AIR-01).
2. Requeue/park mechanism for capacity- or quota-held runs (delay topic vs DB-backed dispatcher) and its ordering guarantees per `tenantId:runId` key (AIR-01).
3. Composition admission vs `maxConcurrentRuns` (reservation, exemption, or slot release) (AIR-02).
4. Pre-call prompt-token estimation method per provider, usage-field extraction per provider (incl. streaming), and token/cost recording for abandoned or cancelled in-flight calls (AIR-05).
5. Per-`ModelDescriptor` capability declaration and how capabilities of admin-registered local models are discovered/validated (probe vs declaration) (AIR-04).
6. Mid-stream provider failover behavior for SSE surfaces (AIR-10).
7. Cancel propagation to child runs; lock/slot release on terminal transitions (AIR-09).
8. Per-replica concurrent-run slots on `ai` workers and the sizing formula against NFR-013 (AIR-11).
9. What happens when a tenant admin re-routes an agent to a model family the active templates were never evaluated on (AIR-12).
10. Reference hardware for NFR-013 (already PRD §11 open question #8 — restated here because every AI capacity claim hangs on it).

## 7. Risks

### Scalability
- Rebalance storms under load are a self-amplifying failure: load → long runs → poll-interval eviction → redelivery → duplicate claims contending on Redisson locks → more lag → HPA adds replicas → more rebalances (W1, W11). Probability ~certain without AIR-01; blast radius is the whole AI tier (ingestion/analytics groups are separate — good isolation per ArchitectureOverview D5).
- No run-throughput capacity model: operators cannot predict report-storm drain time or NFR-013 compliance headroom (W7-adjacent, AIR-11).

### Operational
- Cost dashboards and `maxCost` silently inert on local-only deployments — admins get false comfort from configured ceilings (W6).
- Cancel that does not verifiably release concurrency slots/locks leaks capacity until TTLs expire (W9).

### Data consistency
- At-least-once + resumable steps + idempotent tools (§3.2, §4) is sound. Residual: duplicate concurrent claims during rebalance rely entirely on the Redisson lock; the lock's TTL/renewal semantics for 60-min runs are unspecified (folded into AIR-01 — a lock expiring mid-run re-admits the split-brain the state machine assumes away).

### Tenant isolation
- QoS isolation: head-of-line blocking on shared partitions lets one capped/noisy tenant delay others' runs (W2). Data isolation itself is well covered (§4 rules 1–2, §7.1, NFR-041 suite).

### AI safety
- Validation quality on small local models bounds the whole guardrail chain: a weak Validation Agent model passes weak checks. Cross-model checking (§5.16) exists but is optional ("where the routing table allows"). Covered by AIR-07/AIR-08.
- Guardrail/eval hard bars in gating CI verify plumbing, not model behavior (Contradiction 1); real-model behavior is only observed nightly and non-blocking — a prompt regression that breaks real-model JSON output can merge green (AIR-08).

### Implementation
- Publishing the provider SPI with provider-level capabilities (W4) creates a semver-breaking change the first time someone routes to a multi-model Ollama host — which is the default deployment. Fix costs one line today, a major SPI version later.

## 9. Area verdict & conditions

**Verdict: READY WITH CONDITIONS.** Mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items.

The agent runtime design is unusually mature on lifecycle, budgets, auditability, isolation, and degradation — the fundamentals are right and nothing in the committed envelope requires an architectural redesign. But four documented behaviors are, as written, unimplementable or self-contradictory, and all four sit on the critical path of Phase 3:

- **AIR-01** — `eip.ai.jobs` claim/offset/poll-decoupling semantics (long runs break consumer-group membership; queue-hold blocks partitions).
- **AIR-02** — Report Composition fan-out deadlock under `maxConcurrentRuns`.
- **AIR-03** — gating-eval contradiction (AgentArchitecture §9 vs TestingStrategy/AIValidationWorkflow).
- **AIR-04** — per-model capability declaration in the LLM provider SPI before the SPI is published under semver.

These four are MANDATORY: fix in the source documents before any `eip-ai`/`eip-workers` implementation task starts. AIR-05 through AIR-13 are RECOMMENDED by Sprint 3 / next design iteration; AIR-14/AIR-15 are consciously accepted with stated ceilings.

## 10. Inviolable principles

1. **AI is additive, never load-bearing** (AgentArchitecture §1.2, §13): every non-generative capability must function with zero LLM providers configured; generative failure never blocks ingestion, analytics, dashboards, or RBAC.
2. **Numbers come from tools, never from model recall** (§1.3): any numeric or factual claim in an agent output must trace to a tool result, enforced by the Validation Agent fact check.
3. **No unvalidated user-facing output, ever** (§6.2, FR-087): the fact/citation/schema baseline cannot be disabled by tenants or bypassed by retries exhausting — exhaustion fails the run.
4. **Principal and tenant propagation without escalation** (§4 rules 1–2): tool calls run under the initiating principal's RBAC and injected tenantId; the model never controls tenant scope; RLS is the backstop.
5. **Every LLM call audited, including cache hits, fallback hops, and abandoned calls** (§11, §10, §2.2): no code path may call a provider outside the audited `llm_call` funnel.
6. **Budgets are hard stops enforced pre-call** (§3.3): no run continues past token/cost/step/tool/wall-clock ceilings; overflow fails loud (`BUDGET_EXCEEDED`), never silently truncates mandatory evidence (§3.4).
7. **Kafka group membership must never depend on run duration**: job claim and run execution are decoupled; the run store, not redelivery, is the recovery mechanism (post-AIR-01, this is law).
8. **A cancelled run never publishes partial artifacts** (§2.2) and always releases its concurrency slot and locks (post-AIR-09).
