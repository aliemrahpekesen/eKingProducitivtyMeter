## 2. Extreme-scenario assessment

| Trace volume at 1M events/h with 100% always-on classes | **Holds — but the sampling design is internally contradictory** | Volume math is fine: 10% API head sampling + 1–10% background (§4) keeps span rates modest even at 10×; 100% for agent runs/LLM/report/DLQ/migrations is low-volume by nature. With 10% parent-based head sampling, 90% of 5xx spans never reach the Collector — tail sampling cannot resurrect them. Principle 2 (§1: "every user-visible symptom must be walkable dashboard → trace → logs") is unsatisfiable in the allowed minimal production config. | 30d raw + enterprise long-term metrics, air-gapped | **Degrades — story unnamed** | §2 retention table says "enterprise: + long-term store" and §8.1 mentions "remote-write lag in enterprise long-term-store setups" — but no component is ever named (Thanos? Mimir? customer-provided?). Worse, the air-gap image manifest (DeploymentModel §7 step 1) lists OTel Collector, Prometheus, Grafana — but **not Tempo, Loki, Alertmanager, or any long-term store**, so the optional/enterprise observability components cannot even be mirrored per the documented procedure | Name the long-term store; add Tempo/Loki/Alertmanager/long-term-store + exporters to `images.yaml` and DeploymentModel §5 sizing (OBS-05) |
| Fully air-gapped: dead-man switch & self-monitoring | **Degrades** | §8.1's Watchdog "routed to a heartbeat integration" is the classic pattern for an *external SaaS* receiver (healthchecks.io/PagerDuty) — impossible air-gapped, and no on-prem receiver is specified. Prometheus is single-replica in every topology diagram (DeploymentModel §2–§4); if it dies, all §7 alerts die, and only the (unspecified) watchdog would notice. Alertmanager has no deployable entry, replica count, or sizing anywhere in DeploymentModel | Specify the on-prem heartbeat receiver; state the Prometheus/Alertmanager HA stance per topology or record the accepted risk (OBS-08) |
| SLO burn-rate correctness at scale | **Holds** | Verified the multi-window math (§8): 14× over 1h = 14/720 ≈ 1.94% ≈ "2% of 30d budget" ✓; 6× over 6h = 5% ✓; 3× over 24h = 10% ✓; 1× = steady pace ✓ (14× is a benign rounding of the canonical 14.4). SLIs are defined as ratios/compliant-window shares, so burn-rate is implementable. One gap: report-success and AI-completion SLIs are low-count (a handful of jobs/h at small installs) — a 5m/1h fast-burn window will flap without a minimum-traffic guard | Add min-traffic guard or accept documented flap risk (OBS-10) |

## 3. Strengths

- **Cardinality rules are stated and governed.** ObservabilityModel §1 principle 3 bans unbounded labels explicitly (`no entityId, no user ids, no free-text`); ObservabilityRequirements §3 turns this into a merge requirement (PR must list each label and its bounded value set) with TSDB head-cardinality guards as backstop (§8.1). No `team` label exists anywhere in the platform catalog — team is product data, not telemetry dimension. This is the right structure; only the numbers are missing.
- **Readiness-probe policy is exemplary and consistent.** §9: liveness never checks dependencies; readiness gates only on Postgres + Flyway; Kafka/Redis are degraded-not-unready (NFR-020). This matches AP-6 and prevents the classic cascading-restart failure. The earlier inconsistency was caught and fixed (docs/reviews/DocumentationQualityReview.md #18).
- **Burn-rate SLO framework is correct** (verified above), with an explicit error-budget policy (§8) and a deliberate, defensible exclusion of connector-target outages from the freshness SLO.
- **Meta-monitoring exists at all** (§8.1) — absence alerts, collector self-metrics, TSDB cardinality watch, dead-man switch. Most architectures this age don't have the section; this one only needs air-gap grounding.
- **Governance actually bites.** G6 (ObservabilityRequirements) is unusually strong: uncataloged `eip_*` metric fails docs-lint (G7) *and* G6; empty observability-delta is a failure, not an implicit none; SLI/SLO changes require R-OE approval + docs PR first. "Unobservable = unfinished" is a CLAUDE.md law. The enforcement loop is real.
- **Dashboards-as-code is committed**: `/infra/grafana` JSON versioned with the release, provisioned in all topologies, update-in-same-PR required (ObservabilityRequirements §6).
- **Audit↔trace correlation design (§10)** is thorough: always-sampled auditable flows, root-span rule so `traceId` is never `-`, retention-alignment reasoning, exemplar deep-links.
- **Two lag signals kept deliberately** (records-behind for HPA, time-lag for SLO — §3), with the cross-listing to EventModel §12 explicit.

## 4. Weaknesses

- **No numeric cardinality budget anywhere.** "Cardinality budgets are reviewed per metric at code review" (§1) is a process, not a budget. There is no per-install active-series target, no per-metric-family allocation, and observability-stack sizing (DeploymentModel §5) is visibly not derived from the label math (2 vCPU/8 GB small-prod cannot hold the committed-envelope estimate of 300k–800k series alongside Grafana and the Collector).
- **`connector` label semantics undefined** (type vs instance id) — a 25× cardinality swing at envelope; `stream` and `reason` label bounds unstated (ObservabilityModel §3).
- **Sampling architecture contradiction** — head sampling at SDK vs tail-sampling 5xx at Collector (§4/§2), detailed in §2 above.
- **The §7 alert table's runbook links are all dead.** Every alert carries a `runbook` annotation pointing at anchors like `../operations/OperationsGuide.md#api-errors`, `#dlq-drain`, `#pg-replication`, `#connector-down` — **none of these anchors exist in OperationsGuide.md** (its sections are `§3.1 DLQ replay`, `§4` alert table, etc., with different names). The G6 rule "an alert without a runbook line fails G6" (ObservabilityRequirements §6) is violated by the architecture documents themselves before a line of code exists.
- **Missing infrastructure alerts in the shipped rule set** (§7): nothing for Postgres-down/failover event, Kafka broker down / under-replicated or offline partitions (dashboard panel exists, §6, but no rule), disk pressure (only in OperationsGuide §4 as `DiskPressure` with no PrometheusRule counterpart), Redis down, MinIO, Keycloak/OIDC, cert expiry (`CertExpirySoon` in OperationsGuide §4 has no defined metric source — who exports cert-expiry timestamps in Compose, where cert-manager doesn't exist?).
- **Backing-service metric sources unspecified.** The Database & Cache and Kafka & Queues dashboards (§6) need pg_stat_statements/replication-lag/broker-ISR/Redis metrics; KubernetesOpenShift.md §Monitoring names ServiceMonitors for app pods and Strimzi brokers only. No redis exporter, MinIO scrape endpoint, Keycloak metrics, or Compose-topology exporter story anywhere.
- **`eip.outbox.lag_seconds` is missing from the source-of-record catalog.** EventModel §9 defines it ("Relay lag is a first-class metric, alert > 60 s") and BackendPlan lists it as a golden signal, but ObservabilityModel §3 (declared source of record, ObservabilityRequirements §3) omits it, §7 has no outbox alert, and no dashboard panel shows it. Same for `webhook_intake_buffer` depth (DataFlow §3).
- **Per-tenant SLO blindness (minor).** All §8 SLOs are per-install; at 50 tenants a single tenant's connector-driven freshness collapse can hide inside the 99% global budget. Acceptable for MVP; worth stating explicitly.

## 5. Contradictions

1. **Two disjoint alert catalogs.** ObservabilityModel §7 defines `EipConnectorDown`, `EipDlqNonEmpty`, `EipKafkaConsumerLagGrowing`, `EipIngestionFreshnessSloBurn`; OperationsGuide §4 runbooks a different set — `ConnectorDegraded`, `DlqDepthHigh`, `ConsumerLagHigh`, `IngestionFreshnessSloBreach`, plus alerts with no §7 rule (`DiskPressure`, `RedisDown`, `CertExpirySoon`, `AuditWriteFailure`, `RagIndexStale`, `WebhookIntakeErrors`). An implementer cannot tell which names are the contract.
2. **Three DLQ alert definitions.** ObservabilityModel §7: `increase(...[10m]) > 0` warning, critical > 100/h. EventModel §10: "depth > 0 for 15 min ⇒ warning; > 100 events or growth > 10/min ⇒ page", on a *different metric* (`eip.consumer.dlq.routed` vs `eip_kafka_dlq_messages_total`). OperationsGuide §4: `DlqDepthHigh` with an unspecified threshold.
3. **Metric naming/labels diverge between BackendPlan and ObservabilityModel.** BackendPlan §Observability: `eip.ingestion.events.processed{topic,group,outcome}`, `eip.analytics.metric.compute.duration{metricKey}`, mandatory tag `tenant`. ObservabilityModel §3: `eip_ingestion_events_total{tenantId,connector,entityType,outcome}`, `eip_analytics_metric_compute_duration_seconds{metric_family}` (6 bounded values vs per-`metricKey` — a real cardinality difference), label `tenantId`. ObservabilityRequirements §3 blesses dotted ids "where they render to the catalog's Prometheus name" — these do not.
4. **Dashboard names.** OperationsGuide §3/§5/§13 instructs operators to open "EIP Overview" and "Capacity" dashboards; ObservabilityModel §6 ships exactly seven dashboards and neither name is among them.
5. **Runbook anchors** (doc-vs-doc, load-bearing): §7's `runbook` annotations vs OperationsGuide's actual heading set — no anchor matches (see §4 Weaknesses).
6. **Log retention framing.** ObservabilityModel §2 note says the audit log is "25 months"; OperationsGuide §8 says "audit store retention is a compliance setting (default 400 days)". (Full retention reconciliation is FMA-01 in the companion review; noted here because §2's table repeats the number.)

## 6. Missing decisions

- Long-term metrics store for enterprise (Thanos vs Mimir vs customer APM via Collector) — affects air-gap manifest, sizing, remote-write config, and the §8.1 remote-write-lag meta-monitor.
- Sampling decision point: SDK-head vs Collector-tail split (who drops what, and what the SDK exports).
- `connector` label identity (type vs instance) and the bounded value sets for `stream`, `reason`, `purpose`.
- Per-install active-series budget and per-family allocation; TSDB head-series alert threshold number.
- Alertmanager topology: replicas, sizing, grouping keys, inhibition rules, and how per-tenant thresholds (`EipLlmCostAnomaly`) are injected into static rules.
- On-prem Watchdog heartbeat receiver for air-gapped installs.
- Prometheus HA stance (single instance accepted? HA pair with dedup? per topology).
- Exporter set per backing service, per topology (incl. Compose).
- Minimum log-aggregation requirement for production (Loki/SIEM mandatory or not), and log-volume budget.
- Whether per-tenant SLO slicing is ever offered (deferred is fine — decide explicitly).

## 7. Risks

### Scalability
- Series explosion at 10× tenants/integrations if `connector`=instance or `stream`=namespace; single-Prometheus ceiling reached with no named scale-out component (§2 rows 1–2, 6).
- Observability stack sizing (DeploymentModel §5) under-provisioned even at committed envelope; risk of the monitoring system being the first thing to fall over during the incident it should be observing.

### Operational
- Dead runbook links + duplicate alert taxonomies → on-call confusion in the first real incident; alert-storm fatigue at 100+ integrations trains operators to ignore pages.
- Loki-optional production → post-incident forensics impossible beyond trace retention (14d) once container logs rotate.
- Air-gapped installs cannot mirror Tempo/Loki/Alertmanager per the documented §7 manifest; dead-man switch has no receiver.

### Implementation
- G6 requires implementers to cite catalog entries and runbook anchors that don't exist or conflict — the gate will either be waived (eroding governance) or block Phase 0/1 velocity on doc archaeology. Fixing docs first is cheaper.

### Tenant isolation
- `tenantId` on metrics is fine (ids only), but Grafana is a shared operator surface: per-tenant cost/usage panels (AI/LLM dashboard, §6) expose tenant activity to any Grafana viewer. No Grafana RBAC/tenant-visibility statement exists. Low severity on-prem (operator-only), worth one sentence in SecurityModel/ObservabilityModel.

### AI safety
- Solid: span attributes never carry prompt text (§4), 100% sampling of LLM calls with audit join, cost anomaly alert. No additional exposure found.

## 9. Area verdict & conditions

**Verdict: READY WITH CONDITIONS.** Mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items.

The observability architecture is structurally strong — correct probe policy, verified burn-rate math, real governance teeth (G6), disciplined catalog, dashboards-as-code — and there is a credible scale-out path for every extreme scenario. But the alert/runbook contract is broken across documents, the sampling design is self-contradictory, and a critical signal (outbox lag) is missing from the declared source of record. These are cheap to fix now and expensive after Phase 0 wires G6 to them.

## 10. Inviolable principles

1. **Readiness gates on PostgreSQL + Flyway only.** Kafka and Redis are degraded-not-unready, forever; liveness never checks dependencies (ObservabilityModel §9, NFR-020, AP-6). No implementation may add a hard readiness dependency.
2. **No unbounded metric labels.** Never `entityId`, user ids, raw paths, free text, or per-namespace/per-instance identifiers as label values; every new label ships with an enumerated bound in the catalog PR (ObservabilityModel §1, ObservabilityRequirements §3).
3. **Unobservable = unfinished.** Every new endpoint/consumer/job/failure mode ships metric + trace + structured log + alert + runbook anchor in the same PR (G6); the ObservabilityModel §3 catalog is the single source of record for metric names.
4. **Auditable flows are never sampled away.** Agent runs, LLM calls, secret/KMS operations, DLQ handling and migrations are 100%-traced; `traceId` is never `-` on an auditable action; the audit↔trace join must survive Tempo's absence.
5. **Telemetry never contains secrets, PII, prompt/completion bodies, or member identities**; telemetry is never a substitute for the audit log (separate retention, separate guarantees).
6. **The Collector is the single telemetry egress**; deployables never talk to backends directly; zero phone-home in any topology, including observability.
7. **Silence is never health.** Every always-emitting signal has an absence alert; the alerting path itself carries a dead-man switch with an on-prem receiver.
