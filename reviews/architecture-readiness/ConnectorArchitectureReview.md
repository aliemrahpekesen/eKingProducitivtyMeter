> Reviewer: Enterprise Integration Architect · Date: 2026-07-06 · Verdict: **READY WITH CONDITIONS** — mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items.

## 1. Scope & reviewed documents

## 2. Extreme-scenario assessment

| Scenario | Holds / Degrades / Breaks | Reasoning (cited) | Mitigation path |
|---|---|---|---|
| **100+ configured integrations — scheduler fairness, starvation, thundering herd** | **Breaks** (as specified) | Three documents describe three fragments of one mechanism that is never assembled: BackendPlan chooses **Quartz clustered JDBC-store** ("exactly-one-node execution", explicitly rejecting "a bespoke DB-lease"); DataFlow Flows A/B say `SS->>SJE: SyncJob (Redisson lease per instance)`; ConnectorFramework §4 says Redisson locks prevent double-runs and promises "round-robin across tenants and instances" fairness with **no mechanism**. There is no sync-job queue or topic (EventModel §3 has no `eip.sync.*`), so a Quartz trigger executes the sync in-process on whichever worker node claimed it — no global concurrency cap exists (`maxConcurrentStreams` is per-instance only; 100 instances × 3 streams = 300 concurrent syncs with nothing bounding a single node). Misfire policy after downtime is "per job class" (BackendPlan) but unspecified for sync jobs: after a multi-hour outage, all 100+ triggers misfire simultaneously — a thundering herd against the worker pool, Redis, and every source. Schedule-phase jitter is absent: `syncIntervalMinutes` default 15 (ConnectorFramework §12) aligns ticks across instances created together. | CON-02 (MANDATORY): specify dispatch model, Quartz↔Redisson layering, per-node/global concurrency caps, misfire = reschedule-with-jitter, per-instance phase offset. Nothing forecloses the fix — Quartz + a bounded executor + jittered triggers is implementable — but today an implementer invents all of it ad hoc. |
| **10 Jira instances × one Jira Data Center — shared source-side budget** | **Degrades** | `RateLimitPolicy` and the Redis budget are strictly **per instance** (ConnectorFramework §2, §5: "Budget is shared across worker replicas per instance"). Ten tenants' instances against one Jira DC each get 50 req/min (§11.1 default) = 500 req/min aggregate against one server that budgets globally. Each instance honors `Retry-After` independently, so they collectively re-storm in lockstep after every 429 window. No cross-instance/per-host budget grouping exists anywhere. Also: on Redis loss, rate limiters "fall back to conservative in-process limits" (ArchitectureOverview §9) — with N worker replicas, N in-process limiters can aggregate above the configured ceiling. | CON-05: optional budget-group key (default: source host) sharing one Redis budget across instances; document the Redis-down aggregate-ceiling caveat. Migratable later (rate-limiter key change), hence RECOMMENDED. |
| **Initial full sync of a 10M-issue Jira (changelog amplification)** | **Breaks** | At the §11.1 default budget (50 req/min) and Cloud's `maxResults ≤ 100`, 10M issues = ≥100k search calls ≈ 33 h of paging alone. Changelog: `expand=changelog` is "capped per issue, page the rest via `/changelog`" (§11.1 quirks) — the per-issue paging path is up to one extra call *per issue with a deep changelog*; worst case approaches 10M extra calls ≈ **139 days** at the default budget. No bulk-export path or changelog budget strategy is specified. Worse, BackendPlan's TimeLimiter is "**2h per full sync run**" while ConnectorFramework §4 says backfills run as chunked 30-day slices — "run" vs "slice" is unreconciled, and DataFlow §10 Flow A's own target (≥50 rec/s, 100k-item Jira ≤ 60 min) means even the committed 1M-item tenant (~5.6 h) is killed by its own timeout as written (also flagged as EDA C5). | CON-03 (MANDATORY): reconcile TimeLimiter semantics with chunked backfill; document the changelog-fetch budget strategy and an honest onboarding-duration formula; declare the 10M-issue ceiling as ACCEPTED-RISK with the JQL-windowing partition strategy (`updated ASC` re-anchor per §11.1 is the right primitive and already documented). |
| **Incremental correctness — deleted-item detection at 10M issues** | **Breaks** (silently) | `updated >= watermark` polling structurally cannot see deletions in Jira/Confluence/GitHub/GitLab/Bitbucket/SonarQube list APIs. §7 states "webhooks may be lost; syncs reconcile" — true for upserts, **false for deletes**: a missed `issue_deleted` webhook is never repaired by any documented mechanism, and 8 of 18 catalog entries have no webhooks at all. DataFlow §9 says canonical "Soft-delete via source tombstones" and EventModel §4.2 defines `workitem.deleted`, but **no §11 catalog entry documents how tombstones are produced** (only Docker Registry's tag-diffing implies it). Over years, ghost rows accumulate and silently corrupt flow/WIP/aging metrics — at 10M issues, materially. | CON-04 (MANDATORY): per-catalog-entry "Deletion detection" row (webhook tombstone / periodic key-scan reconciliation sweep / API support / none-declared) plus a `RawSink` tombstone emission contract. Retrofitting tombstones into the raw-record contract after Phase 1 connectors ship changes a CC-1 contract anchor — decide now. |
| **Push/streaming connectors under a batch SPI (OTLP intake, K8s watch)** | **Breaks** (SPI cannot express its own catalog) | The SPI (§2) is exclusively batch: `fullSync()`/`incrementalSync(checkpoint)` invoked by a scheduler, cancellation checked "between pages". Yet §11.13 OTLP is "a **push receiver**, not a puller" ("Incremental: N/A — continuous push") and §11.8/11.9 Kubernetes/OpenShift are **list+watch** — a long-lived streaming connection with no pages and no natural run end. Neither archetype has defined semantics for scheduling, lease renewal, run duration vs the 2h TimeLimiter, DEGRADED transitions, or checkpointing. The SPI is a semver'd, third-party-implementable contract anchor (NFR-060, FR-018, QualityGatePolicy G4); shipping v1 without a streaming/push archetype forces a MAJOR bump the moment Phase 5 connectors are built. | CON-01 (MANDATORY): define connector archetypes (BATCH_POLL / STREAMING_WATCH / PUSH_INTAKE) in §2 with lifecycle and scheduler semantics per archetype, before SPI implementation begins. |
| **Missed-webhook reconciliation** | **Holds** (for upserts) | §7 is explicit and correct: webhooks are "a latency optimization, never a second code path"; the same raw-record shape enters the identical staging→normalize path; periodic incremental syncs remain the source of completeness; delivery-ID replay protection with 24 h Redis TTL; webhook/sync convergence is asserted by the test kit (TestingStrategy §5.3). One of the best-specified parts of the framework. | Deletion case folded into CON-04; otherwise none. |
| **Checkpoint corruption & connector upgrades with in-flight checkpoints** | **Degrades** (undefined recovery) | `StreamCursor` is opaque JSONB (`core.connector_checkpoint.cursor`, DatabasePlan §3). §2.1 versions the **SPI**, not the **cursor format**: nothing specifies what happens when connector v2 loads a v1 cursor it cannot parse, or a corrupted cursor. The only documented recovery is the admin-UI forced re-sync (§4) — an operator action, not a defined failure mode. A 10M-issue instance whose cursor breaks on upgrade silently faces a multi-week re-backfill. | CON-07: cursor schema-version field, validation on load, defined fallback ladder (re-anchor from `watermark` → per-stream reset), and a cursor-migration obligation in §2.1 + §13. |
| **Third-party connector build (FR-018)** | **Degrades** | FR-018: third parties implement connectors "without modifying core modules". ConnectorFramework §13 step 1: "Implement `Connector` in a **new `eip-connectors` submodule**; register … via the SPI service loader" — an in-repo change, contradicting the requirement. No packaging/loading model (plugin JAR? classloader isolation? how does an air-gapped site deliver it into the `eip-workers` image?), and no published test-kit artifact (the `ConnectorContractTestKit` exists in-repo, TestingStrategy §5.3 — good — but its distribution to external implementers is unspecified). Normalizer/schema registration for external connectors is likewise open (also EDA W8). | CON-08: define the external packaging/registration path and publish the TCK; until then FR-018 is aspirational. |
| **Private CA / egress proxy / air gap, per instance** | **Degrades** | Air-gap posture overall is genuinely strong (simulation mode §10, no phone-home, NFR-051, KubernetesOpenShift §14). But TLS trust and proxy are **global only**: one JVM truststore populated at startup and one `HTTPS_PROXY`/`NO_PROXY` set per Deployment (KubernetesOpenShift §5.2). With 100+ integrations spanning network zones (some behind the proxy, some direct; different internal CAs; sources requiring client mTLS), per-instance TLS/proxy config does not exist — the Jira config schema (§12) has no `tls`/`proxy` block and no `mTLS` auth method. Adding a CA means restarting every worker. | CON-09: optional per-instance `tls` (CA bundle ref, client-cert credentialRef) and `proxy` override in config-schema conventions (§8/§12); global truststore stays the default. |
| **Source pathologies: 429 storms, 5xx flapping, silent truncation, partial 403** | Holds / **Degrades on partial visibility** | 429/5xx handling is solid: full-jitter backoff, `Retry-After` honoring, 50%-over-20-calls breaker with probe-based recovery (§5). Truncation ceilings are honestly documented per source (SonarQube 10k ceiling + partitioning, GitLab offset cap → keyset, Prometheus 11k points — §11.6/11.4/11.11). The gap is **partial permission loss**: §5 classifies 401/403-after-refresh as "fail the stream run immediately" — so one revoked repo/project scope halts an entire stream; the only alternative an implementer can invent is silently skipping, i.e. unflagged partial data. No mechanism carries connector-level completeness into FR-060's uncertainty indicators, so analytics trust degrades invisibly. | CON-06: per-scope 403 semantics (mark scope EXCLUDED with reason, continue, emit completeness metadata + metric); CON-13 (ACCEPTED-RISK): generic fetched-vs-source count reconciliation deferred to FR-041. |
| **Confluence 500k pages — blobs and ACLs** | **Degrades / Breaks (ACLs → RAG)** | Windowed CQL backfills and separate attachment rate limits are documented (§11.2 quirks). But (a) attachment blob volume is unbounded — no size cap/MIME filter config, while k8s-prod MinIO sizing is 250 Gi × 4 EC:2 (KubernetesOpenShift §7): one large Confluence exceeds it; (b) **no permissions/restrictions stream exists** in §11.2, yet Confluence is a primary RAG source (DataFlow Flow F) with "permission-aware retrieval" — permissions here are EIP RBAC, not source ACLs. A page restricted to 5 people in Confluence becomes retrievable by any EIP user with tenant document scope. | CON-11 (source-ACL decision, before the Confluence connector and ideally before RAG GA hardening), CON-14 (attachment filters + sizing guidance, ACCEPTED-RISK with documented ceiling). |
| **OTLP intake as push at high volume** | **Degrades** | Backpressure to senders is properly specified: per-tenant byte/span budgets, 429 + `Retry-After`, collectors retry natively (§11.13) — the right contract. But EventModel §9 routes **all** publication through the Postgres outbox, and §11.13 never says where span-batch → reference/aggregate reduction happens relative to raw staging. If every OTLP batch becomes a `raw_*` row + outbox row, high-volume telemetry intake funnels through the pipeline's narrowest point (the single outbox relay — EDA W2). Default budget values are also unstated, so "admission control" is unenforceable as written. | CON-12: specify the reduction point (at the receiver, before raw staging) and default per-tenant budgets. |
| **Kubernetes connector at 1,000+ namespaces** | **Degrades** | Watch mechanics are technically correct (resourceVersion, 410 re-list-as-reconciliation, chunked lists, client QPS 20/40 — §11.8). But §11.9 says cluster-scoped listing is "frequently forbidden — operate namespace-scoped with a configured namespace allow-list": at 1,000 namespaces × ~5 resource types that is ~5,000 concurrent watch connections from one connector instance — no fan-out budget, connection-pool bound, or shared-informer strategy is documented. And **no least-privilege RBAC manifest for the customer cluster exists anywhere** — the single most-asked question in an enterprise security review of this connector ("what exactly does your ServiceAccount read?"). | CON-10: RBAC Role/ClusterRole manifests (read-only verbs, resource list) + a documented namespace-scale strategy (cluster-scoped watch where permitted, watch-budget cap + partitioned re-list where not). |
| **100k repositories / GitHub GraphQL at 10×** | Holds (degrades honestly) | Cost-point limits, node caps, secondary rate limits, `since`-vs-push-time, squash-merge linkage are all documented with correct mitigations (§11.3). GitHub App installation tokens are correctly preferred for higher budgets. Sync duration scales linearly with budget — slow but honest, resumable per-stream, and never impacts dashboards (DataFlow Flow A). | None at this layer; onboarding-duration formula from CON-03 should cover SCM too. |

## 3. Strengths

1. **Catalog quirk depth is exceptional.** §11 documents real, load-bearing API pathologies with correct mitigations: Jira JQL pagination instability → `updated ASC` re-anchor (§11.1); GitLab 50k offset ceiling → mandatory keyset (§11.4); SonarQube 10k result ceiling → query partitioning (§11.6); Prometheus 11k-point chunking and retention-honest backfills (§11.11); Bitbucket Cloud/DC API split (§11.5); Docker multi-arch digest identity (§11.10). This is knowledge that normally costs months of production incidents.
2. **Single-pipeline webhook stance.** §7: webhooks converted to the same raw-record shape, same staging→normalize path, "never a second code path", with polling as the completeness backstop and delivery-ID replay protection. Structurally eliminates the webhook/poll divergence class of bugs.
3. **Idempotency layering.** `ExternalRef` natural-key upserts + SHA-256 content-hash suppression (§6) means overlap windows and forced re-syncs converge quietly; checkpoint commit only after durable staging (§4) closes the loss window. GA criterion §14 "Resume" and test-kit K4/K6 verify it.
4. **Simulation mode as a first-class delivery requirement** (§10): deterministic, cross-connector-consistent, exercising the full pipeline including checkpoints and rate limiters — the air-gap/demo/test story most platforms never get. K7 enforces byte-identical determinism.
5. **Secrets discipline**: credential references only, `secretPointers()` declared, resolution at sync start, memory-only, audited (§8); §14 has an explicit no-credential-in-any-log criterion.
6. **Per-instance failure isolation** is coherent end-to-end: own breaker, budget, checkpoint rows, scheduler slot (§5); lifecycle DEGRADED semantics (§3) with probe-based auto-recovery; ArchitectureOverview §9 confirms the blast radius.
7. **SPI semver policy** (§2.1) with registration-time MAJOR refusal — the compatibility gate exists and fails closed.
8. **Governance genuinely covers this area**: ConnectorFramework SPI is a CC-1 contract anchor requiring G4 architect review (QualityGatePolicy; CLAUDE.md), and the `ConnectorContractTestKit` K1–K7 is ArchUnit-enforced on every connector (TestingStrategy §5.3, TestingChecklist) — new connectors *cannot* ship without contract coverage.
9. **Observability metric set** (§9) covers the operational questions that matter: checkpoint lag, breaker state, rate-limit remaining, per-class errors, parked records — wired to a defined health monitor and alert thresholds.

## 4. Weaknesses

1. **The sync dispatch/fairness layer is a name, not a design.** "Round-robin across tenants and instances" (§4) has no mechanism; Quartz vs Redisson layering is unassembled across three documents; no global concurrency cap, no misfire policy for sync jobs, no schedule jitter (§2 row 1). At 100+ instances this is where the system falls over first.
2. **Rate limiting has no concept of a shared source.** Per-instance budgets only (§2, §5); N instances against one host multiply the configured budget and synchronize their 429 recovery (§2 row 2).
3. **Deletion is unspecified for every polling connector.** "Syncs reconcile" (§7) does not cover deletes; no catalog entry documents delete detection; the tombstone production path for DataFlow §9's "source tombstones" does not exist (§2 row 4).
4. **The SPI cannot express two of its own mandatory catalog members** — OTLP push intake (§11.13) and K8s/OpenShift watch (§11.8/11.9) have no archetype in §2 (§2 row 5).
5. **Full-sync duration is internally contradictory and unbudgeted for changelog amplification** — 2h TimeLimiter (BackendPlan) vs 30-day chunked backfills (§4) vs DataFlow §10 Flow A durations; Jira changelog paging cost is named as a quirk but never given a strategy or budget (§2 row 3).
6. **Partial visibility is binary**: 403 fails the whole stream (§5) or an implementer silently skips; no completeness metadata reaches FR-060's uncertainty indicators (§2 row 10).
7. **Cursor format has no versioning or corruption story** despite being opaque JSONB owned by a versioned connector implementation (§2 row 7).
8. **FR-018 third-party path is contradicted by the framework's own checklist** (§13 step 1 requires an in-repo submodule) and has no packaging/distribution model for air-gapped sites (§2 row 8).
9. **TLS/proxy is deployment-global** (KubernetesOpenShift §5.2) — no per-instance CA bundle, client mTLS, or proxy override for mixed-zone enterprise estates (§2 row 9).
10. **No customer-side least-privilege RBAC manifest** for the Kubernetes/OpenShift connector; no watch fan-out budget at 1,000+ namespaces (§2 row 13).
11. **Test kit and GA criteria omit the new failure classes**: K1–K7 (TestingStrategy §5.3) and §14 GA criteria cover resume/rate-limit/idempotency/webhooks/secrets/simulation, but not delete propagation, partial-visibility flagging, cursor-format migration, or misfire/herd behavior — so even after CON-01..CON-07 land, nothing gates them without CON-15.

## 6. Missing decisions

An implementer will be forced to decide ad hoc:

1. **Sync job dispatch**: how a Quartz trigger's work reaches/spreads across `eip-workers` replicas; whether a sync-job queue exists; per-node and deployment-wide concurrent-sync caps; Quartz misfire policy per sync job class; schedule-phase jitter. (CON-02)
2. **Connector archetypes**: SPI shape and lifecycle for streaming (watch) and push (OTLP) connectors — run duration, lease/heartbeat, checkpoint semantics, DEGRADED transitions. (CON-01)
3. **Delete detection per connector**: tombstone source (webhook / key-scan sweep / API), sweep cadence, and the `RawSink` tombstone record shape. (CON-04)
4. **Changelog/backfill budget strategy for Jira at scale** and the sync-run vs backfill-slice timeout semantics. (CON-03)
5. **Shared-source rate budget grouping** (key: baseUrl host? explicit budget-group id?) and Redis-down limiter behavior across replicas. (CON-05)
6. **Partial-visibility semantics**: per-scope 403 handling, completeness metadata schema, and its propagation to FR-060 indicators. (CON-06)
7. **Cursor format versioning/migration** across connector implementation versions; corruption fallback ladder. (CON-07)
8. **External connector packaging** (plugin JAR + classloader isolation vs separate deployable), air-gapped delivery, TCK distribution, third-party normalizer/schema registration. (CON-08)
9. **Per-instance TLS/proxy overrides** vs global truststore/proxy; whether client mTLS becomes a supported `AuthMethod`. (CON-09)
10. **K8s connector RBAC manifest and namespace-scale watch strategy** (cluster-scoped watch vs per-namespace fan-out budget). (CON-10)
11. **Source-ACL handling for RAG-bound documents** (map restrictions to retrieval filters, or exclude restricted content by configuration). (CON-11)
12. **OTLP reduction point and default admission budgets** relative to raw staging/outbox. (CON-12)

## 7. Risks

### Scalability
- **Onboarding wall**: 10M-issue sources are practically un-onboardable at documented defaults (weeks–months); even committed-envelope tenants collide with the 2h TimeLimiter as written (§2 rows 1, 3; C3). Without CON-02/CON-03, the first large enterprise deal becomes a production incident.
- **Scheduler herd**: post-outage misfire of 100+ triggers can saturate the worker pool and re-trigger source rate-limit bans (429 escalating to temporary IP bans on Jira Cloud/Bitbucket).
- **K8s watch fan-out** at 1,000 namespaces (~5k connections) with no budget (§2 row 13).

### Security
- **RAG ACL leak**: Confluence/document restrictions not ingested ⇒ restricted source content retrievable tenant-wide via RAG (§2 row 11). Compounding: retrieval audit exists (DataFlow Flow F) but audits the leak, doesn't prevent it.
- **Missing least-privilege manifest** for the customer-cluster ServiceAccount invites over-granting (cluster-admin-shaped kubeconfigs) at exactly the customer boundary enterprises scrutinize most.
- Strengths that reduce risk: credential-ref-only configs, sync-start resolution, §14 no-credential-in-logs gate.

### Operational
- Quartz/Redisson layering ambiguity (C4) means Redis-down behavior is undefined in practice: Quartz keeps firing (Postgres-backed) while lock acquisition fails — is that a skipped run, an error, DEGRADED? Operators cannot write a runbook against three documents that disagree.
- Backfill-duration alerting: checkpoint-lag and DLQ alerts (§9) will fire continuously during any legitimate large backfill; no suppression policy (shared with EDA finding 10).

### Data consistency
- **Ghost rows from undetected deletes** silently inflate WIP/aging/flow metrics forever (§2 row 4) — an analytics-trust defect invisible to users because FR-060 indicators receive no connector completeness signal (§2 row 10).
- Content-hash suppression (§6) is sound, but hash covers the "normalized-relevant payload subset" — subset changes across connector versions silently re-emit or suppress events; tie the subset definition to the cursor/version contract in CON-07.

### Tenant isolation
- Per-instance isolation is strong, but the shared-source budget gap (§2 row 2) means tenant A's aggressive backfill consumes the *source-side* budget of tenant B's instance against the same Jira DC — cross-tenant interference outside EIP's isolation model, invisible to EIP's fairness controls.

### Implementation
- The `ConnectorContractTestKit` (K1–K7) and §14 GA gates enforce yesterday's contract; without CON-15 they will green-light connectors that ignore every fix in this review.

## 9. Area verdict & conditions

**Verdict: READY WITH CONDITIONS.** Mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items.

The connector framework's core contracts — checkpointed resumable syncs, ExternalRef idempotency, single-pipeline webhook intake, per-instance isolation, simulation mode, secrets discipline — are genuinely enterprise-grade, and the catalog's per-source quirks show unusual real-world depth. Governance (CC-1 anchor status, ArchUnit-enforced test kit) actually enforces the contract. But four gaps sit on the Phase 1 critical path and change contract-anchor shapes if deferred:

Conditions gating readiness (must be fixed in source documents before implementation tasks start):

- **CON-01** — SPI archetypes for push/streaming connectors (the SPI must be able to express its own catalog before it is frozen and semver'd).
- **CON-02** — sync dispatch/fairness/misfire design (the sync engine cannot be implemented from the current three-document fragments).
- **CON-03** — full-sync duration/TimeLimiter reconciliation + changelog budget strategy (as written, committed-envelope full syncs kill themselves).
- **CON-04** — per-connector delete detection + RawSink tombstone contract (retrofitting tombstones later changes the raw-record contract anchor and leaves analytics silently wrong meanwhile).

CON-05..CON-12 and CON-15 are due by Sprint 3 / next design iteration; CON-13/CON-14 are consciously accepted with documented ceilings.

## 10. Inviolable principles

1. **SyncContext is the sole channel.** Connectors never touch Kafka, Postgres, Redis, or MinIO directly (ConnectorFramework §2) — all durable effects flow through `RawSink`/`CheckpointStore`.
2. **Webhooks are a latency optimization, never a second code path.** Every intake mode converges on the identical raw-record → staging → normalize pipeline; polling (and, once specified, reconciliation sweeps) remains the source of completeness — including deletions.
3. **Checkpoints commit only after raw records are durably staged and published.** No acknowledged-data-loss window, ever; a killed sync resumes, never restarts from zero.
4. **Replays converge.** ExternalRef natural-key upserts + content-hash suppression make overlapping windows, forced re-syncs, and DLQ replays idempotent and downstream-quiet.
5. **One instance's failure never blocks another.** Breaker, rate budget, checkpoints, and scheduler slot are per instance; degradation is isolated and auto-recovering.
6. **Source protection over sync speed.** Every outbound call is bounded by a rate limiter honoring server signals; sources without formal limits get conservative self-throttles; the configured ceiling is never breached — including in aggregate across worker replicas and (once CON-05 lands) across instances sharing a source.
7. **Credential references only.** Raw secrets never appear in configs, checkpoints, logs, metrics, error payloads, or the UI; resolution is per-run, in-memory, audited.
8. **Simulation mode exercises the real pipeline.** Same checkpoints, rate limiter, staging, and events — never a shortcut path; determinism is contract-tested.
9. **No per-user data collection.** No connector stream may collect or emit individual-activity data beyond team-mapping metadata (PRD FR-057, NFR-071 — release-blocking).
10. **The SPI is a semver'd published contract.** Breaking changes bump MAJOR with a deprecation window; a registered connector is never silently broken by a platform upgrade, and cursor/checkpoint state must survive (or deterministically migrate across) connector version changes.
