## 2. Extreme-scenario assessment

| Scenario | Holds / Degrades / Breaks | Reasoning (citations) | Mitigation path |
|---|---|---|---|
| PostgreSQL RLS at 10× tenants (500+) | **Holds** | DatabasePlan §5 is verified-correct pooling design: `eip_app` with `NOBYPASSRLS` + `FORCE ROW LEVEL SECURITY`, transaction-scoped `SET LOCAL app.tenant_id` via datasource decorator (§12) — HikariCP-safe by construction; no-default GUC errors loudly on wiring bugs. No LISTEN/NOTIFY dependence (Kafka carries events, EventModel §9); locks are Redisson, not pg advisory — so future transaction-pooling PgBouncer wouldn't break session-state assumptions (`SET LOCAL` is transaction-scoped). | Kafka shared topics, many tenants | **Degrades (accepted-in-effect, not accepted-in-writing)** | Topics are shared, keyed `tenantId:entityId` (EventModel §7) — per-tenant broker ACLs are structurally impossible on shared topics; a consumer bug that trusts row data over the envelope is a cross-tenant read. Mitigations exist and are gated: consumers must resolve tenant context from the envelope before any DB access (EventModel §8; SecurityChecklist §3.1), isolation suite A4 includes "Kafka envelope `tenantId` validation", DLQ browsing is tenant-scoped + RBAC-guarded (EventModel §10). All consumers are EIP-owned — tenants never touch the broker directly. But no document states this residual risk and its acceptance explicitly. | MTR-03: write the accepted-risk statement + the invariant ("envelope tenant wins; mismatch → DLQ + alert") in EventModel/SecurityModel. |
| One tenant syncs 10M Jira issues while others use dashboards | **Degrades** | Dashboard reads are insulated at the DB layer: precomputed `ops.metric_value` by PK + MVs (DatabasePlan §8), separate small analytics pool so batch never queues dashboards (§12), key includes `entityId` so the bulk sync spreads across all 12 partitions (EventModel §7). Autovacuum pressure from the bulk upsert is tuned for (§9) but shared. | MTR-05: document the noisy-neighbor analysis and add per-tenant ingest throttling (token bucket at raw-intake/normalizer) + partition-skew alert (exists: 3× median, EventModel §7) tied to per-tenant pause controls. |
| Redis under many tenants | **Degrades** | Namespacing `eip:{tenantId}:...` is convention enforced only by code review (SecurityModel §5 "no cross-tenant key access in code review checklist") — acceptable given Redis holds no durable-of-record data (DatabasePlan intro). But eviction fairness is unaddressed: one tenant's cache churn evicts every tenant's entries (shared LRU), and rate-limit/quota state is documented fail-open on Redis loss (DeploymentModel §9: "rate-limit counters may reset") — i.e., quota enforcement lapses exactly when the system is stressed. | MTR-04: document per-tenant cache budget policy (or explicitly accept shared-LRU with the fail-open consequence), and state the quota-lapse window on Redis failover as a conscious decision. |
| MinIO at 10× tenants | **Ambiguous — decision missing** | SecurityModel §5: "Bucket-per-tenant **or** tenant prefix + per-tenant credentials/policies" — an unresolved *or* in the isolation table itself. If the app uses one credential with prefix conventions, isolation is app-code-only (no IAM backstop, unlike the DB's RLS backstop). SecurityChecklist A4 tests "MinIO prefix isolation", quietly presupposing the prefix model. At 500+ tenants, bucket-per-tenant strains MinIO bucket/IAM management; prefix + per-tenant policy scales but must be chosen and specified. Object-key layout is expensive to migrate later. | MTR-02 (MANDATORY): pick the mechanism, state whether per-tenant IAM credentials/policies are enforced (backstop) or app-enforced-only (accepted), align A4. |
| Vector store at 10× (30–40M chunks) | **Degrades, with one contradiction** | pgvector: RLS on `rag_chunk` + SPI-injected tenant filter (RAGArchitecture §9) is sound. At 10× the D3 envelope (10M chunks), a single shared HNSW index with tenant+ACL filtering degrades: pgvector's filtered HNSW over-scans for small tenants (filter selectivity vs. `ef_search`); sizing guidance (§15) covers memory but not filtered-recall behavior at high tenant counts. Scale-out path exists (Qdrant via SPI, read replicas — §15) — not foreclosed. **Contradiction:** SecurityModel §5 says "separate Qdrant collections per tenant when Qdrant is used"; RAGArchitecture §3.2 says "Qdrant collection per model" with tenant payload filters (§9). | MTR-01 (MANDATORY): resolve the Qdrant isolation model contradiction. MTR-08: document filtered-HNSW behavior and the Qdrant migration trigger. |
| LLM layer, many tenants on shared inference | **Holds** | AgentArchitecture §7.1 is exemplary: KV/prefix/prompt caches disabled or `tenantId`-partitioned, adapter refuses non-compliant shared endpoints, embedding batches never mix tenants, CI shared-endpoint isolation scenario (NFR-041). Response cache keys include `tenantId` + `principalGrantHash` (§10). Per-tenant model routing + pinned dedicated endpoints available. | None needed. This is the strongest layer reviewed. |
| Per-tenant quotas at 100+ connectors | **Degrades until Phase 3** | Enforcement points: ingest — connector-instance outbound rate limits (FR-015, Phase 1) + RAG indexing limits; AI — quota ledger, enqueue-time rejection, claim-time `maxConcurrentRuns` (AgentArchitecture §10, FR-130 P1/Phase 3); API — FR-144 per-tenant rate limits are **P1/Phase 3**. | Tenant offboarding at many tenants | **Degrades** | OperationsGuide §3.4 Decommission covers Postgres RLS scope, vector/RAG rows, MinIO prefix, secrets destruction, Kafka key-space aging via retention — good skeleton. | Cross-tenant support access (break-glass) | **Degrades (under-specified)** | SecurityModel §4: PLATFORM_ADMIN "cannot silently read tenant business data: cross-tenant data access requires explicit, audited support-access grant"; §11 has `support.access.granted`; DatabasePlan §5 routes cross-tenant admin through SECURITY DEFINER functions with own audit events. ## 3. Strengths

1. **RLS design is verified-correct, not aspirational.** `FORCE ROW LEVEL SECURITY`, `NOBYPASSRLS` app role, transaction-scoped `SET LOCAL` via a single datasource decorator, erroring GUC default, repeatable-migration policy catalog, restore-time RLS smoke test (DatabasePlan §5, §12, §13). The failure mode of a missed application predicate is "zero rows", not "breach".
2. **Defense in depth is real at every DB touchpoint:** application predicate + RLS backstop + isolation test suite on every PR with no waiver allowed (SecurityChecklist A4; NFR-041 CI-verified). Governance names the exact platform-scoped RLS exceptions and requires dual sign-off for new ones (SecurityChecklist §3.1; DatabasePlan §2).
3. **AI/RAG isolation is thorough end to end:** SPI-injected tenant filter that is not caller-suppliable, per-principal retrieval caching (`principalGrantHash`), tenant-partitioned indexing keys, ACL filter push-down into the vector query, and an honest documented residual (ACL revocation staleness window with a ≤15-min guidance and a security-classified freshness metric) (RAGArchitecture §8–§9).
4. **Shared-inference isolation (AgentArchitecture §7.1)** — tenant-partitioned or disabled cross-request caches with an adapter-level refusal and a CI scenario — addresses a leak class most multi-tenant AI platforms haven't named yet.
5. **Kafka consumer conventions make the shared-topic model workable:** envelope-first tenant resolution before DB access, manual ack after idempotent write, tenant-scoped DLQ admin (EventModel §8–§10).
6. **Tenant lifecycle has a real skeleton:** suspend (drain + checkpoint), decommission with completion report, per-tenant logical export via SECURITY DEFINER `COPY` for portability (OperationsGuide §3.4; DatabasePlan §13).

## 4. Weaknesses

1. **The isolation-summary table contains an unresolved architectural choice.** "Bucket-per-tenant or tenant prefix" (SecurityModel §5) is the only isolation layer specified as a disjunction; every other layer names one mechanism. Object storage is also the only layer with no independent backstop if the prefix-convention path is chosen.
2. **Qdrant isolation model is contradicted across documents** (SecurityModel §5 per-tenant collections vs. RAGArchitecture §3.2/§9 per-model collections + payload filter). The two models have different blast radii and different scale ceilings at 500+ tenants.
3. **No noisy-neighbor blast-radius analysis exists anywhere.** Individual mitigations are scattered (partition-skew alert, analytics pool, KEDA scaling) but no document answers "what does tenant B experience while tenant A backfills 10M issues, and what bounds it?" — the question every enterprise security/platform review will ask.
4. **Offboarding purge is unverifiable as written.** No completeness matrix, no verification queries, no statement about backups or DLQ residue (OperationsGuide §3.4).
5. **Redis fairness and quota fail-open are undocumented decisions.** Eviction is shared-LRU across tenants; rate-limit state resets on failover (DeploymentModel §9) — both may be acceptable, neither is consciously accepted in writing.
6. **Quota enforcement is asymmetric across the three planes:** ingest (partial, connector-side only), AI (strong), API (absent until Phase 3, FR-144 P1); FR-130's storage quota has no enforcement mechanism documented at all.

## 6. Missing decisions

1. **Object-storage isolation mechanism** — bucket-per-tenant vs. prefix; per-tenant IAM policies as backstop or app-enforced-only. Hard to migrate after Phase 1 lays down key layouts. (MTR-02)
2. **Qdrant collection topology** — per tenant, per model, or per tenant×model; and the enforced invariant either way. (MTR-01)
3. **Per-tenant ingest fairness mechanism** — where the throttle lives (raw intake, normalizer consumer, or connector scheduler), and the bound on cross-tenant freshness impact. (MTR-05)
4. **Redis multi-tenant policy** — shared LRU accepted or per-tenant budgets; quota behavior during Redis failover (fail-open window). (MTR-04)
5. **Storage-quota enforcement point** (FR-130 lists storage; no mechanism documented anywhere). (MTR-10 scope)
6. **Support-access grant parameters** — duration, scope, approver, tenant visibility. (MTR-07)
7. **Offboarding verification** — what constitutes proof of purge per store; backup-retention disclosure to the departing tenant. (MTR-06)

## 7. Risks

### Tenant isolation
- **R1 (High until MTR-02/MTR-01 land).** Object storage and Qdrant are the two isolation layers where the mechanism is ambiguous; ambiguity in an isolation layer is itself a defect because implementers, testers (A4), and auditors will each resolve it differently.
- **R2 (Medium, residual, accepted-in-effect).** Kafka shared-topic consumer-bug risk: a single misbehaving consumer that trusts payload over envelope reads cross-tenant. Mitigations are strong (envelope-first rule, isolation suite, EIP-only consumers) but the risk acceptance is implicit (MTR-03).
- **R3 (Low).** RAG ACL staleness window is documented and bounded — a model of how residual risk should be handled. No action.

### Scalability
- **R4 (Medium).** Whale-tenant sync degrades every tenant's freshness SLO via shared consumer groups; at the committed envelope KEDA scale-out absorbs it, at 10× it needs the MTR-05 throttle. Not foreclosed — consumers are idempotent and per-tenant pause switches exist (SecurityModel §14).
- **R5 (Medium at 10×).** Filtered HNSW on one shared pgvector index degrades for small tenants at 30M+ chunks; migration path (Qdrant SPI) exists but its trigger is unstated (MTR-08).

### Operational
- **R6 (Medium).** An enterprise or regulator asking "prove tenant X is gone" cannot be answered with the current §3.4 procedure (MTR-06).
- **R7 (Low-Medium).** Quota lapse during Redis failover is invisible to operators unless documented and alerted (MTR-04).

### Data consistency
- **R8 (Low).** Decommission leaves tenant-keyed events in DLQs and outbox/dedup tables until retention/cleanup; a replay after decommission would resurrect orphan rows (RLS makes them unreadable, but they exist). Fold the "no replay for decommissioned tenants" rule into MTR-06.

## 9. Area verdict & conditions

**READY WITH CONDITIONS.** Mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items.

The core isolation architecture — RLS as verified backstop, envelope-first Kafka tenancy, SPI-enforced vector filtering, tenant-partitioned inference caching, and a CI isolation suite that cannot be waived — is coherent, mutually reinforcing, and honestly documented where residual risk exists (RAG ACL staleness). The committed envelope (50 tenants) is comfortably within design. The blocking defects are two isolation layers whose *mechanism* is ambiguous or contradicted across documents — ambiguity that the governance gates themselves (A4) have already started encoding one way.

**Conditions gating readiness (fix in source docs before any Phase-0/1 implementation task touching the affected stores):**

- **MTR-01** — Qdrant isolation model contradiction resolved
- **MTR-02** — object-storage isolation mechanism decided and backstop stance stated

MTR-03–MTR-09 are due by Sprint 3 / next design iteration (MTR-05 and MTR-06 before the first multi-tenant pilot). MTR-10 is accepted for MVP with the stated ceiling and triggers.

## 10. Inviolable principles

1. **Every tenant-owned row carries `tenant_id` with forced RLS; the application predicate is the mechanism, RLS is the backstop — both always present** (FR-128; DatabasePlan §5; CLAUDE.md law 5).
2. **Tenant binding is transaction-scoped `SET LOCAL` only — never session-scoped, never string-concatenated, never model- or caller-suppliable** (DatabasePlan §5; AgentArchitecture §4 rule 2; SecurityChecklist §3.1).
3. **Consumers derive tenant context from the event envelope before any data access; payload/row data never overrides the envelope** (EventModel §8).
4. **Isolation filters live inside the SPI/platform layer (VectorStore, ToolRegistry, storage client), never delegated to callers** — a caller that forgets a filter must be structurally unable to leak (RAGArchitecture §9; SecurityModel §4).
5. **No shared cross-tenant cache or inference state without `tenantId` (and, where permission-relevant, `principalGrantHash`) in the key** (AgentArchitecture §7.1, §10; RAGArchitecture §8).
6. **Isolation test failures are never merged around — no waiver exists for A4** (SecurityChecklist §2; NFR-041).
7. **Cross-tenant access by platform operators is explicit, granted, time-boxed (post-MTR-07), and audited — no silent path, including SECURITY DEFINER functions** (SecurityModel §4; DatabasePlan §5).
8. **Tenant deletion must be provable per store** (post-MTR-06) — a purge without a verification artifact is not a purge.
