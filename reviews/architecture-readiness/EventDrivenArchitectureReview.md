## 3. Strengths

1. **Outbox-everywhere with real atomicity semantics.** EventModel §9 routes *all* publication — including raw and webhook intake — through the transactional outbox, with the no-lost/no-ghost property stated and covered by tests (EventModel §15 "outbox tests"). BackendPlan §6 gives a defensible Debezium-free rationale for on-prem with a preserved CDC upgrade path behind the same table.
2. **The not-event-sourced stance is explicit and structurally enforced.** EventModel §11: PostgreSQL is the system of record; 7–90 d retention makes infinite-replay dependencies "structurally impossible by design." This is the single most important scale-protecting decision in the document set — rebuilds and 10M-issue history live in the DB, not the log.
3. **Idempotency is layered, and correctly ordered.** eventId (UUIDv7) dedup or natural-key upserts (EventModel §1–2), manual ack strictly after the idempotent write ("Never ack-then-write", EventModel §8), crash-between-write-and-ack convergence tested (§15). Dedup is scoped per consumer group (DatabasePlan §2).
4. **Honest hot-partition analysis.** EventModel §7 correctly reasons that `tenantId:entityId` spreads a large tenant, identifies the true residual risk (single hot entity, e.g. flapping alerts), prescribes debounce coalescing, and *explicitly rejects key salting* to preserve ordering. No hand-waving.
5. **Schema evolution rules are tight where it matters.** Additive-only minors enforced by CI schema diff (EventModel §6, §15 contract tests — including doc examples as fixtures), unknown-MAJOR ⇒ DLQ + page (§5), upcast-on-consume so handlers see one shape.
6. **Governance actually enforces this area.** PerformanceChecklist §6/§6.1 hard-wires EventModel §8 batching defaults, the outbox-only rule ("direct Kafka publication is a BLOCKER regardless of throughput"), lag-SLO declaration, and outbox-lag thresholds into the CC-3 gate; QualityGatePolicy makes EventModel a CC-1 contract anchor requiring architect review. This is better-than-typical governance for a messaging layer.
7. **Lag measured as time-lag, not offset-lag** (EventModel §12), with per-family SLOs and stated backpressure behavior per flow (DataFlow §1–8) — the right metric for freshness NFRs.
8. **Testcontainers-not-embedded-Kafka decision** (EventModel §15) with the rule that no test may assert delivery semantics against embedded — prevents a whole class of false-green delivery tests.

## 4. Weaknesses

1. **No bulk/backfill fast path.** Every ingestion mode — 10M-issue initial sync and single webhook alike — shares one pipeline, one topic set, one throughput envelope (DataFlow Flow A; EventModel §3). Large-tenant onboarding is therefore both slow (§2 row 1) and a noisy neighbor for co-tenants' NFR-012 freshness. FR-039 (raw replay/backfill, P1) implies the same shared path.
2. **Outbox relay is an unsized singleton.** BackendPlan §8 makes the poller a non-concurrent Quartz job; EventModel §9 gives it a lag alert (>60 s) but no throughput target, no batch-size spec, no scale-out design. Since raw *and* domain events pass through it, it is the narrowest point of the entire pipeline — and `core.event_outbox` (DatabasePlan §2) is an unpartitioned insert+delete hot table with no churn/vacuum guidance.
3. **Retry policy has no failure taxonomy** beyond schema-validation (EventModel §10). Transient infra failure is indistinguishable from poison data: both DLQ after ~71 s of retries. See §2 retry-storm row.
4. **`processed_events` write amplification is unbudgeted** — absent from DatabasePlan §6 partitioning and §9 capacity planning despite being a top-3 table by row count at the committed envelope (~500M rows/35 d across ~6 groups). Whether the ledger insert commits in the same transaction as the handler's canonical write (required for the crash-redelivery guarantee) is implied but never stated; nor is it stated which consumers may skip the ledger via structural idempotency (EventModel §2 permits it, ComponentModel §9's IdempotencyGuard "before any consumer handler runs" suggests it is unconditional).
5. **Partition counts are specified (good) but provisioning rationale is not.** EventModel §3 fixes 6/12/6/3 and §7 says counts are "provisioned generously up front" — with no per-partition throughput assumption, no growth trigger, and the repartition runbook existing only as a forward reference (§13 "runbooks … live with /infra/kubernetes" — a directory that does not exist yet). At 10×, 12 partitions is not generous.
6. **DLQ mechanics don't survive contact with Kafka's immutability.** Inspect-by-page, discard-by-msgId (EventModel §10; APIDesign §4.3) require a parked-message index/store that no document defines; replay of large DLQs is unthrottled.
7. **Upcaster support window is undefined.** EventModel §15 tests "oldest supported minor" round-trips, but no document defines what the oldest supported minor *is* or ties it to the real requirement: it must cover domain-topic retention (30 d) **plus** DLQ retention (30 d) plus replay, or DLQ replay after an upgrade hits removed upcasters.
8. **Third-party connectors vs the in-repo schema registry.** FR-018 (P1, Phase 2) admits external connector implementations, and EventModel §6's revisit trigger is "if non-EIP producers must publish to `eip.*` topics." Third parties publish raw events via `RawEmitter` (schema-free payloads — fine), but who ships their normalizers and domain schemas, and how those register into the in-repo registry, is unspecified.

## 6. Missing decisions

An implementer will be forced to decide ad hoc:

1. **Backfill/onboarding lane** — dedicated `eip.raw.<connector>.backfill` topics, consumer-priority scheme, or per-tenant pause/quota at consume time; and the FR-130 quota enforcement point in the Kafka lane. (No document decides.)
2. **Outbox relay throughput target, batch size, poll mechanism** ("short interval" Quartz job — Quartz's ~1 s trigger floor vs a long-running loop job is unresolved), and the scale-out design (shard claim by `hash(partition_key)` preserves per-key order — nothing forecloses it, nothing specifies it).
3. **Transient-vs-poison failure classification** and the consumer behavior for infra outages (pause/seek vs DLQ).
4. **DLQ parked-message storage model** — pure Kafka topic vs DB-backed park index; what `DELETE /dlq/.../messages/{msgId}` physically does; replay throttling.
5. **`processed_events` transactional semantics** (ledger insert in the same TX as the canonical write?) and the ledger-vs-structural-idempotency decision per consumer group.
6. **Deployment ordering across `eip-app`/`eip-workers`** for schema MAJOR bumps and consumer-first upgrades.
7. **Oldest supported minor / upcaster retention window** relative to topic + DLQ retention.
8. **Third-party connector (FR-018) schema/normalizer registration** path into the in-repo registry.
9. **Partition-count growth triggers** and the drain-and-cutover runbook content (currently a name, not a procedure).
10. **Backfill-aware alerting** — outbox lag >60 s and DLQ-depth pages will fire continuously during any legitimate large sync; suppression/window policy undefined.

## 7. Risks

### Scalability
- **R1 (High).** Single non-concurrent outbox poller + unpartitioned `event_outbox` is the pipeline-wide bottleneck; every raw and domain event crosses it twice per source record. Holds at 100k/h (~70 rows/s), unproven at burst ×3 with backfill, breaks at 10× absent sharding (EDA-07).
- **R2 (Medium).** 12-partition domain topics cap consumer parallelism; repartitioning is a disruptive, runbook-gated operation not yet written (EDA-08).
- **R3 (Medium).** `processed_events` churn (~14M rows/day at envelope, ~10× that in extreme) with batched hard deletes will bloat and stall vacuum on the same PG instance serving dashboards (EDA-04).

### Operational
- **R4 (High).** Transient infra outages convert to mass DLQ routing + paging across ~30 groups; recovery is manual replay per group (EDA-03).
- **R5 (Medium).** DLQ admin API as specified is unimplementable over raw Kafka topics (discard-by-id); teams will improvise divergent park stores (EDA-09).
- **R6 (Medium).** MAJOR-bump rolling upgrades between the two deployables trigger unknown-MAJOR DLQ floods until ordering is codified (EDA-10).
- **R7 (Low).** Alert fatigue during legitimate backfills (outbox lag, consumer lag, DLQ growth thresholds all fire) trains operators to ignore pages (EDA-11).

### Data consistency
- **R8 (Low — well-mitigated).** At-least-once with per-group dedup and manual-ack-after-write is coherent and test-covered; the residual risk is only C1: if any code path follows the DataFlow diagrams (direct produce) instead of EventModel §9, the no-dual-write guarantee silently disappears. The docs must agree before Phase 1 (EDA-01).

### Tenant isolation
- **R9 (Medium).** Shared per-connector-type raw topics mean one tenant's volume degrades every tenant's freshness SLO; isolation is data-correct (tenantId + RLS from envelope) but not performance-isolated (EDA-06).

### Implementation
- **R10 (Medium).** Contradictions C2/C3 (group ownership, eip-app consumption) will produce wrong consumer wiring in Phase 1 scaffolding if not resolved first — these are exactly the conventions the ArchUnit topic-consumption tests (ComponentModel §10) will encode, so getting them wrong bakes the error into the enforcement layer (EDA-05).

## 9. Area verdict & conditions

**Verdict: READY WITH CONDITIONS.** Mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items.

The event-driven core is architecturally sound: outbox-based atomic publication, at-least-once + layered idempotency, retention-bounded topics with PostgreSQL as the system of record, honest partitioning analysis, CI-enforced schema evolution, and governance (PerformanceChecklist §6/§6.1, CC-1 anchor status) that genuinely enforces the contracts. The committed NFR envelope (100k events/h, 1M WorkItems, 50 tenants) is reachable on this design. The 10× extreme scenarios degrade rather than break *provided* the backfill lane, relay sizing, and partition-growth work is done — none of the current choices forecloses the scale-out path.

## 10. Inviolable principles

1. **Outbox-only publication.** No producer — normalizer, sync run, webhook handler, metric engine, or API — ever writes to Kafka outside the transactional outbox. Direct publication is a build-breaking violation (PerformanceChecklist §6.1), not a review comment.
2. **At-least-once, never exactly-once assumptions.** No component may depend on exactly-once delivery across the pipeline; every consumer is idempotent via eventId dedup or natural-key upsert, and duplicate delivery is a non-event (EventModel §1–2).
3. **Manual ack strictly after the idempotent write commits.** Never ack-then-write; crash windows resolve by redelivery + dedup (EventModel §8).
4. **Per-key ordering is sacred; keys are never salted.** `tenantId:entityId` ordering is the only ordering guarantee; cross-entity/cross-topic ordering must never be assumed; any fairness or throughput mechanism that breaks per-entity ordering is forbidden (EventModel §7).
5. **Kafka is transport, not truth.** PostgreSQL is the system of record; topics are retention-bounded and are never replayed to reconstruct primary state; rebuilds beyond retention come from canonical tables (EventModel §11–12).
6. **Every envelope carries `tenantId`, and consumers bind RLS from it before any table access.** Tenant isolation in the async path is structural (RLS), not a WHERE clause (DataFlow global invariants; FR-128/129).
7. **Schema minors are additive-only, enforced in CI; unknown MAJOR never gets guessed** — it DLQs and pages (EventModel §5–6, FR-038).
8. **DLQ routing commits the offset — a poison message never blocks a partition** — and every DLQ discard is audited (EventModel §10).
9. **The dedup ledger retention must always exceed the longest topic retention plus the replay window** (DataFlow §9; DatabasePlan §10) — shrinking it below that re-opens the duplicate window.
10. **Delivery semantics are only ever tested against a real broker** (Testcontainers); embedded Kafka may never back a delivery-semantics assertion (EventModel §15).
