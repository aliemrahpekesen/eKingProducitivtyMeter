## 1. Scope & reviewed documents

This review stresses the documented architecture against the extreme enterprise tier (~10× the committed NFR envelope) and answers, per dimension: does the design hold, degrade gracefully, or break — and is a credible scale-out path preserved or foreclosed.

**Committed envelope (calibration baseline):** [PRD §6](../../docs/product/PRD.md) — ≥10k repositories (NFR-001), ≥1M WorkItems (NFR-002), ≥100k events/h + 3× burst (NFR-003), ≥50 tenants (NFR-004), dashboard p50<500ms/p95<2s (NFR-010); [ArchitectureOverview §1 D3](../../docs/architecture/ArchitectureOverview.md) — 5,000 active engineers, 500 tool instances, 2,000 sync jobs/h, ~10× internal design headroom (≈300 events/s), 100M canonical records, 10M RAG chunks.

**Extreme tier (this review's stress input):** 500+ teams · 10,000+ users · 100,000+ repositories · 10,000,000+ Jira issues · 1,000,000+ deployments · 1,000+ customer-side K8s namespaces (polled) · 100+ integrations · very large Confluence spaces · high-volume OTLP intake · many tenants · air-gapped/local-LLM-only.

## 2. Extreme-scenario assessment

Load arithmetic used throughout: 100k events/h ≈ **28 events/s**; 3× burst ≈ 83/s; documented design headroom ≈ **300 events/s ≈ 1.08M events/h** (ArchitectureOverview §1 D3). Write amplification per source event on the single Postgres primary ≈ 6–10 row writes (raw_* insert + raw outbox row + canonical upsert + `external_ref` probe/update + transition insert + domain outbox row + per-consumer-group `processed_events` dedup rows + metric_value writes; EventModel §9, DatabasePlan §3).

| # | Scenario | Verdict | Reasoning (cited) | Mitigation path |
|---|---|---|---|---|
| 1 | **500+ teams** | **Holds** | Metric series count: ~2,000 subjects (teams+projects+products+BUs+org, PRD FR-059) × ~30 metrics × ~760 daily buckets (25 months, DeploymentModel §5 sizing policy) ≈ 45.6M `ops.metric_value` rows ≈ 5.5 GB at 120 B/row (DatabasePlan §9). Monthly range partitions + PK-only reads (DatabasePlan §4 "Metric reads") keep dashboard queries pruned. 13-month fine-grain retention + rollups (DatabasePlan §10) bounds growth. | None needed. |

Kafka, the read-model layer, and the frontend architecture are not the constraint at any examined tier.

## 3. Strengths

1. **CQRS-lite read models make dashboard latency volume-independent.** Dashboards read `ops.metric_value` by PK with partition pruning and `reports.mv_*` grids — never wide joins at request time (DatabasePlan §8, ADR-011, ArchitectureOverview §8 "Read models"). NFR-010 at 10× row counts is credible because the query cost is a function of series length, not canonical table size. This is the single most important scale decision in the design, and it is right.
2. **Keyset pagination is deep-pagination-proof.** `(tenant_id, updated_at DESC, id)` with UUIDv7 tiebreaker (DatabasePlan §4) is O(page) at any offset; property-based tests assert page-concatenation equivalence (TestingStrategy §18); a 1M-row seed verification is an explicit Phase 0 acceptance item (DatabasePlan §14). Offset pagination is a BLOCKER by governance (PerformanceChecklist §4).
3. **RLS overhead is engineered away, not hand-waved.** Every RLS policy predicate (`tenant_id = current_setting(...)`, DatabasePlan §5) is satisfiable by index prefix because every hot index leads with `tenant_id` (DatabasePlan §4). NFR-010/011 with RLS active is achievable.
4. **Backpressure is lag, never cascade.** Outbox-buffered producers, pull-based consumers, per-connector rate limiters, budget-capped AI jobs (ArchitectureOverview §9; EventModel §12 lag SLOs with per-family backpressure behavior). Overload semantics are explicitly documented per failure mode.
5. **Tenant-partitioning discipline is structurally complete.** `tenant_id` on every row + RLS, Kafka keys `tenantId:*` (EventModel §7), tenant-prefixed Redis/MinIO/vector collections (ArchitectureOverview §6.1), app-generated UUIDv7 (no global DB sequences), cross-schema references as plain UUIDs (DatabasePlan §1). This is exactly the substrate that keeps later per-tenant sharding migratable.
6. **The high-volume tables are partitioned with retention-as-partition-drop** (`metric_value` monthly, `audit_event` monthly, `raw_*` weekly; DatabasePlan §6, §10), with a documented deferred-partitioning trigger for `work_item_transition` (>200M rows).
7. **Frontend scale discipline is unusually concrete for a plan:** CI-enforced bundle budgets (shell ≤250 KB gz, route ≤200 KB gz), virtualization above 200 rows, ECharts canvas for large series, SSE limited to bounded audiences (agent runs/monitors) with automatic polling fallback, TanStack Query as the single cache (FrontendPlan §1, §5, §7, §11).
8. **Governance genuinely enforces perf discipline per PR:** G5/CC-3 requires EXPLAIN (ANALYZE, BUFFERS) at ≥1M-row representative scale, named-query-pattern indexes, mandatory load-scenario triggers by touched area, 10% regression gate, and sizing-impact notes on high-volume tables (PerformanceChecklist §3–§10). This is better than most shipped products have.
9. **Hot-partition analysis is honest:** keying by `tenantId:entityId` spreads hot tenants; salting is explicitly rejected to preserve ordering; single-entity storms get debounce coalescing (EventModel §7).

## 4. Weaknesses

1. **The committed ingest capacity is stated three different ways** (100k/h NFR-003; ~833k/h implied by DeploymentModel §5's "~2M domain events/day per tenant × 10 tenants" sizing baseline; 300 events/s ≈ 1.08M/h D3 headroom). An implementer sizing Topology B cannot tell which number is binding. See §5 C1.
2. **No sharding/read-replica seam is documented.** ArchitectureOverview §8 says only "read replicas are a Phase 5 hardening option"; DatabasePlan has no section on what must remain true for per-tenant DB sharding to stay possible. The seam *exists* (see Strength 5) but is unprotected — nothing in the Architecture Conformance Checklist (ArchitectureOverview §12) or PerformanceChecklist forbids the changes that would foreclose it (cross-tenant joins in app code, DB-global sequences, cross-tenant aggregate tables without a tenant dimension).
3. **Materialized views bypass RLS.** PostgreSQL does not support RLS policies on materialized views, yet `reports.mv_sprint_summary` / `mv_release_readiness` / `mv_team_flow_current` (DatabasePlan §8) aggregate tenant data and are read on dashboard paths, and plain views default to owner-privilege execution (RLS of the *view owner*, not the caller) unless `security_invoker = on`. This collides with FR-128 ("no application query path may bypass RLS for tenant-owned data", PRD §5.8). At 50–500 tenants this is both an isolation and a blast-radius problem (one tenant's refresh cost is every tenant's refresh cost). See §5 C2.
4. **Full-sync throughput is entirely unspecified.** ConnectorFramework documents rate *ceilings* per connector but no throughput *target* (records/s per stream) and no multi-instance parallelization strategy; PRD Open Question 8 (reference hardware) is unresolved. The 10M-issue and 100k-repo arithmetic in §2 (#3, #4) shows wall-clock is the real ceiling — weeks-to-months at documented default budgets.
5. **Outbox relay scale-out is undefined.** EventModel §9 claims per-key ordering "preserved by publishing outbox rows in insertion order per key," but with multiple concurrent relay pollers using `FOR UPDATE SKIP LOCKED`, insertion-order-per-key publication is not guaranteed by anything documented. A single relay is a throughput and availability chokepoint for *every* event in the system (raw + domain + metrics + jobs).
6. **`core.processed_events` write amplification is unsized.** Each ledger-dedup consumer group adds one insert per event with 35-day retention (DatabasePlan §2). At the 300/s headroom with ~4 domain-topic consumer groups that is ~10⁹ rows in the ledger window — yet DatabasePlan §9 has no `processed_events` row, and EventModel §1 leaves ledger-vs-structural idempotency per consumer undecided.
7. **Load-test coverage stops at the envelope floor, below even the sizing baseline.** TestingStrategy §11 tests 100k/h sustained, 300k/h burst, 50 metric-API users, 200 dashboard users. Nothing tests the D3 headroom (300/s), NFR-004's 50 tenants (E7 uses 2), or any extreme-tier ceiling; the `enterprise-large` pack (TestingStrategy §13) has no stated dimensions, so "Performance at full scale targets" (PRD §10 Phase 5) is unfalsifiable as written.
8. **Frontend dashboard refresh behavior is unspecified.** FrontendPlan §4 batches metric queries only "where metric grain and filters coincide" and never states widget auto-refresh intervals; §7 gives a 30 s `refetchInterval` only for connector health. At 10k users, an implementer's ad-hoc choice of per-widget polling is the difference between 11 qps and hundreds of qps on the API tier.
9. **Metric recompute/backfill write storms are under-specified.** FR-062 (new series version per definition change) plus golden-rule recomputation implies bulk rewrites of tens of millions of `metric_value` rows; DataFlow/DatabasePlan document the *read* isolation (dedicated analytics pool, §12) but not write pacing for recompute jobs against the shared primary.

## 6. Missing decisions

Decisions an implementer will be forced to make ad hoc, in scale-impact order:

1. **The database scale-out seam** — which of (a) read replicas for `rm_*`/report reads, (b) per-tenant database sharding via tenant→datasource routing, (c) module extraction with schema split (§2.2) is the sanctioned path at which trigger; and the invariants code must preserve so all three stay possible. (Nothing today forbids a cross-tenant join or a platform-global aggregate table.)
2. **Full-sync throughput target and parallelization** — records/s per stream on reference hardware; whether multiple connector instances/tokens may shard one source system; bulk changelog strategy for Jira (search-API `expand` vs per-issue fetch).
3. **Outbox relay concurrency model** — one relay vs partitioned claimants; how per-key publication order survives >1 relay; relay throughput ceiling and its own scale signal.
4. **Idempotency mechanism per consumer group** — ledger (`processed_events`) vs structural natural-key upsert (EventModel §1 permits either); high-volume consumers must be structural or the ledger becomes a top-5 table.
5. **OTLP intake bounds** — per-tenant span/byte ceilings as numbers; whether OTLP batches traverse raw-staging+outbox or a dedicated admission path; what "reference-only" storage means in rows/bytes.
6. **Widget refresh policy** — default `refetchInterval`/staleTime per dashboard surface; whether `POST /metrics/query` batching per dashboard is mandatory.
7. **Metric recompute pacing** — batch size, pool, and throttle for series-version backfills (FR-062) and `analytics.metric.backfilled` storms.
8. **`enterprise-large` pack dimensions** — the actual tenant/team/WorkItem/repo/event counts that Phase 5 "full scale targets" are certified against.
9. **Replica read-routing semantics** (ties to C5) — which endpoints may serve bounded-staleness reads, and how staleness is surfaced (the `computedAt` convention exists for MVs; nothing equivalent for replica lag).

## 7. Risks

### Scalability
- **R1 (medium/high impact):** Backfill wall-clock at large-customer onboarding (weeks at documented budgets — §2 #3/#4) turns into a sales/POC failure mode long before any runtime limit is hit. Mitigation: SCL-04.
- **R2 (medium):** Single outbox relay saturates or crash-loops → *every* pipeline stalls simultaneously (blast radius exceeds the per-pipeline isolation story of ArchitectureOverview §9). Mitigation: SCL-05.
- **R3 (medium):** Cold-cache dashboard storms after deploys/restarts at 10k users; the 30–60 s TTL cache (ArchitectureOverview §6.5) provides no stampede protection (no documented request-coalescing/single-flight). Mitigation: fold into SCL-07/SCL-09 evidence.
- **R4 (low/medium):** 12-partition ceiling caps normalizer parallelism at ~12 consumers; repartitioning is a planned-change runbook, not an online operation (EventModel §7). Accepted with trigger (SCL-15).

### Data consistency
- **R5 (medium):** Metric recompute storms (FR-062 series versioning) racing live computation on the shared primary; skip-intermediate coalescing (EventModel §12) covers live lag but not bulk rewrite pacing. Mitigation: SCL-08.

### Tenant isolation (scale-coupled)
- **R6 (high if unaddressed):** `reports.mv_*`/plain-view read paths bypassing RLS (C2) — at many-tenant scale this is both an isolation defect and a noisy-neighbor coupling (global refresh cost). Mitigation: SCL-03 (MANDATORY).

### Operational
- **R7 (medium):** Envelope ambiguity (C1) causes under-provisioned Topology B installs that pass NFR-003 tests yet fail real sizing-baseline load. Mitigation: SCL-01 (MANDATORY).
- **R8 (low):** `processed_events` retention deletes (35 d) become a daily multi-million-row delete job competing with ingest I/O. Mitigation: SCL-06.

### Implementation
- **R9 (medium):** Absent documented sharding invariants, ordinary feature work (a cross-tenant admin report, a global uniqueness constraint without `tenant_id`) forecloses per-tenant sharding — the one genuinely hard-to-reverse class of mistake available in this design. Mitigation: SCL-02 (MANDATORY).
- **R10 (low):** Frontend implementers invent per-widget polling → self-inflicted query storm (Weakness 8). Mitigation: SCL-09.

## 9. Area verdict & conditions

**Verdict: READY WITH CONDITIONS.** Mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items.

The core scale architecture — CQRS-lite read models, tenant-keyed partitioned pipelines, keyset pagination, partition-per-time-window storage, lag-not-cascade backpressure — is sound at the committed envelope and degrades gracefully at most of the 10× extreme tier. Steady-state ingest is nowhere near the first bottleneck; the true pressure points are initial backfill wall-clock, the single-primary write path under recompute/backfill storms, and unmeasured 10×-tier read concurrency. No irreversible foreclosure of the scale-out path exists in the design today — but the seam that keeps it open is undocumented and therefore unprotected.

Conditions gating readiness (must land in the source documents before implementation tasks start):

1. **SCL-01** — one binding ingest-capacity number per topology (the current 8× spread between NFR-003 and the DeploymentModel sizing baseline makes capacity planning and G5 evidence ambiguous).
2. **SCL-02** — the scale-out seam (read replicas / per-tenant sharding / module extraction) documented with binding invariants and a conformance-checklist hook, so ordinary implementation work cannot foreclose it.
3. **SCL-03** — resolution of the materialized-view RLS bypass, which contradicts FR-128 on dashboard-serving read paths.

SCL-04 through SCL-12 are required by Sprint 3 / next design iteration; SCL-13/14/15 are consciously accepted ceilings with numeric revisit triggers.

## 10. Inviolable principles

Implementation must never violate these, at any scale tier:

1. **Dashboards never read canonical tables at request time.** All chartable reads go through precomputed `ops.metric_value` series or RLS-protected read-model tables (DatabasePlan §8, ADR-011). A wide join on a dashboard path is a defect regardless of measured latency.
2. **Read load scales with users; write load scales with ingest — and the two never share a queue.** The API tier does no heavy computation and never blocks on Kafka; long-running work is always a worker-side consumer (ArchitectureOverview §8, §12).
3. **Every tenant-owned row carries `tenant_id`; every unique constraint and hot index on tenant-owned data leads with or includes `tenant_id`; tenant-owned IDs are app-generated UUIDv7.** These are the sharding seam. No cross-tenant joins outside audited `SECURITY DEFINER` functions; no DB-global sequences for tenant data.
4. **Cursor/keyset pagination only.** No offset pagination, no unbounded collection reads, no `findAll()` on tenant data (PerformanceChecklist §4–§5 — already BLOCKERs; they stay BLOCKERs forever).
5. **Overload is expressed as measured lag, never as cascading failure or data loss.** At-least-once + idempotent consumers + outbox is the delivery model; nothing may bypass the outbox for event publication, and nothing may require exactly-once broker semantics (EventModel §1, §9; ArchitectureOverview §9).
6. **Time-series and append-only tables are partitioned with retention-as-partition-drop** before they are large, not after (`metric_value`, `audit_event`, `raw_*`; DatabasePlan §6). New high-volume tables must arrive with a partitioning and retention plan or a documented deferral trigger.
7. **Hot-path changes carry evidence, not assertions:** EXPLAIN at representative volume (≥1M-row seed), named-index patterns, matching Gatling scenario, sizing-impact note (PerformanceChecklist G5). A perf claim without CI/load evidence is unverified.
8. **Frontend budgets are CI-enforced invariants:** shell ≤250 KB gz, route chunks ≤200 KB gz, virtualization above 200 rows, one server-state cache (TanStack Query), bounded refresh policies — no per-widget ad-hoc polling loops (FrontendPlan §7, §11).
9. **Scale numbers live in exactly one place per concern** (PRD §6 for commitments; DeploymentModel for sizing derived from them) and are quoted, never re-derived — divergent copies are treated as defects (per PerformanceChecklist §2 discipline).
