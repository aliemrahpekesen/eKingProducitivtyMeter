## 3. Strengths

- **Transactional outbox everywhere** (EventModel §9): no dual-write gap, ghost-event-free, per-key ordered, with relay lag as a first-class alert. This is the correct on-prem answer and it is consistently applied (even raw staging + webhook intake go through it).
- **RLS design discipline** (DatabasePlan §5): `FORCE ROW LEVEL SECURITY`, `NOBYPASSRLS` app role, `SET LOCAL` transaction-scoped GUC with no default (fail-loud), repeatable-migration policy catalog, enumerated no-RLS exceptions (§2) — and governance actually enforces it (SecurityChecklist items make missing RLS a BLOCKER and new exceptions require R-SA + R-DBA sign-off).
- **Honest system-of-record stance** (EventModel §11): short topic retention makes accidental event-sourcing structurally impossible; erasure is a DB operation, not a log rewrite. Exactly right for GDPR-adjacent requirements.
- **Index governance with teeth**: "no index without a named query pattern" + `EXPLAIN (ANALYZE, BUFFERS)` evidence (DatabasePlan §4), operationalized in PerformanceChecklist (named-pattern check, full-partition-scan BLOCKER, sizing-impact note for storage-affecting changes). This is better governance than most shipping products have.
- **Partitioning where it matters** (§6): `metric_value`/`audit_event`/`raw_*` with retention-by-partition-drop, worker-managed (no `pg_partman` dependency — air-gap-aware), and a pre-declared deferral trigger for `work_item_transition` (>~200M rows).
- **Expand–contract migration discipline** (§7): one-way Flyway, batched backfills outside migrations, PG16 non-rewriting defaults, pre-deploy migration job so app pods never hold DDL locks.
- **Sensible pooling** (§12): fixed-size Hikari pools, a segregated analytics pool so batch work can't starve dashboards, PgBouncer explicitly deferred with the transaction-pooling caveat already noted in ArchitectureOverview §6.1.
- **HNSW over IVFFlat with stated reasoning** (§11) and normalized-cosine storage; `maintenance_work_mem` guidance for builds.

## 4. Weaknesses

1. **FR-062 is unimplementable against the §3 schema** — no version dimension in `metric_value` (see §2 table). Retrofitting the PK of the highest-row-count partitioned table is the single most expensive deferred decision in this plan.
2. **Two read-model architectures in the docs** — DataFlow §4 (`metric_facts`, `rm_team_flow_daily`, `rm_sprint_summary`, `rm_dora_daily`, `rm_quality_snapshot`, `rm_ops_health`, `analytics_watermarks`, projector-driven) vs DatabasePlan §8 (`ops.metric_value` + `reports.mv_*` on 5–15 min `REFRESH ... CONCURRENTLY`). ADR-011 and ArchitectureOverview §8 ("rebuildable by replaying `eip.domain.*`") describe the former.
3. **Table catalog is incomplete against the flows.** DatabasePlan §2 claims V1 contains "the full Phase 0 schema", yet these tables named by other documents appear in no schema: `metric_facts`, `rm_*`, `analytics_watermarks`, `risk_assessments` (DataFlow §5), `report_jobs`, `agent_steps`, `report_subscriptions` (DataFlow §7), `webhook_intake_buffer` (DataFlow §3), `rag_index_state`, `rag_retrieval_audit` (RAGArchitecture §10/§13), `metric_definitions`. Each will be invented ad hoc, without §4 index governance or §9 sizing.
4. **§9 sizing omits the biggest tables**: `core.external_ref` (≥1 row per entity per source — strictly more rows than all canonical tables combined), `core.processed_events` (~10⁸–10⁹ rows at design headroom), `core.event_outbox` (highest churn table in the system), `code_review`, and `rag_chunk` at the D3-committed 10M (only the 3M reference figure exists).
5. **Erasure mechanics unspecified where they are foreclosable** (see §2 table): free-form `audit_event.detail`, verbatim PII-bearing text columns, immutable artifacts, Parquet archives. SecurityModel §7's erasure paragraph names the stores but not the mechanism; §11 contradicts FR-142's redaction requirement.
6. **No bloat/vacuum policy beyond three tables** — §9 tunes autovacuum for `work_item`, `pull_request`, `alert` only; nothing for `event_outbox` (insert+delete churn), `processed_events`, `connector_checkpoint` (constant update), `rag_chunk` (delete-then-insert re-index, §Flow F); no REINDEX/pgstattuple bloat policy at all (the quarterly review in §4 drops *unused* indexes, which is a different problem).
7. **`scm.commit` and `scm.pull_request` have no partition trigger** — at the extreme 100k-repo scenario commit is ~10⁸–10⁹ rows; only `work_item_transition` got a deferral threshold (§6).
8. **Retention self-contradiction on metric series** — DatabasePlan §10: fine grain 13 months, rollups 5 years; SecurityModel §7 (declared "single source of record"): metric series *indefinite*; NFR-070: "metric series retained indefinitely unless tenant policy dictates otherwise". Three documents, three answers.
9. **Qdrant migration and per-model embedding storage under-specified / inconsistent** (see §2 table and Contradiction 3).

## 6. Missing decisions

1. **Metric series version key** — column, PK position, dashboard default-version selection, old-version GC (FR-062, PRD Open Q2).
2. **Read-model mechanism** — projector tables vs MVs (Contradiction 1), and the schema/owner of every DataFlow-named table absent from §2.
3. **Rollup storage model** — same table with a grain dimension vs separate `metric_id`s vs a rollup table; and what "rollup job confirms" means before a partition drop (§10).
4. **Erasure mechanics per store** — audit (PII-free-by-construction vs crypto-shred), commit messages/descriptions (pseudonymization pass vs accepted-with-legal-basis), rag_chunk text (re-chunk on erasure), rendered artifacts (delete vs regenerate), Parquet archives (rewrite vs crypto-shred).
5. **RLS overhead budget and whale-tenant plan** — measured delta target, and the escalation option (partition-per-tenant / dedicated instance) if one tenant dominates.
6. **Qdrant migration procedure** — vector copy vs re-embed, cutover criteria, rollback.
7. **Write-throughput budget** — rows/s and WAL MB/s at NFR-003 + headroom, with amplification factors per event (canonical + outbox + dedup + audit).
8. **Backup strategy above a size threshold** — when nightly logical dumps stop and PITR-only begins; restore-time evidence vs RTO.
9. **Partition triggers for `scm.commit` / `scm.pull_request` / `ops.alert`** at high repo counts.
10. **`processed_events` physical design** — partitioned (drop instead of delete) vs batched delete + aggressive autovacuum.

## 7. Risks

**Scalability.** (a) `metric_value` PK retrofit after Phase 2 data exists — days-long backfill on the largest table; avoidable now for the cost of one column. (b) Unbudgeted mega-tables (`external_ref`, `processed_events`, `event_outbox`) discovered in production as vacuum/bloat incidents. (c) `pg_dump`-based logical backups silently aging out of their window as data grows, discovered at restore time.

**Operational.** Bloat on churn tables without a policy; HNSW rebuild windows (≥2 GB `maintenance_work_mem`, hours at 10M chunks) not in any capacity budget; outbox relay is a single logical stage — EventModel §9 preserves per-key order "by publishing outbox rows in insertion order per key", but multi-instance relay claiming with `SKIP LOCKED` can reorder keys across claimers; the concurrency model of the relay is unstated.

**Data consistency.** Restore runbook (§13) re-drives connectors from checkpoints — sound — but read models: if the MV design (§8) wins, MVs restore stale and refresh; if the projector design (DataFlow §4) wins, `analytics_watermarks` must be restored consistently with `metric_facts`; unresolved because of Contradiction 1.

**Tenant isolation.** Strong: RLS forced + governance-enforced; backup §13 requires the post-restore cross-tenant smoke test. Residual: per-tenant logical export runs as `SECURITY DEFINER` — audited per §5, acceptable.

**Security / privacy.** PII foreclosure in append-only/immutable stores (Weakness 5) is the one genuinely irreversible item; everything else in this review is recoverable at a price.

**Implementation / governance.** The EOS checklists are unusually strong on indexes, sizing notes, RLS, and migrations (PerformanceChecklist §"storage-affecting change", SecurityChecklist RLS items, QualityGatePolicy G4 R-DBA review). Gaps: no gate measures RLS overhead; no gate requires a PII-inventory entry when a new column carries personal data (SecurityChecklist covers isolation, not erasure reach); nothing gates that a new table named in a design doc also lands in DatabasePlan §2 (Contradiction 5 shows this drift already happened pre-code).

## 9. Area verdict & conditions

**READY WITH CONDITIONS.** Mandatory conditions were applied in the 2026-07-06 fix wave; remaining conditions are the RECOMMENDED items. The physical design is unusually disciplined for a pre-code project — outbox, RLS enforcement, index governance, partition-drop retention, and expand–contract migrations are all correct and mutually consistent, and the governance checklists genuinely enforce them. Three items gate readiness because they are cheap now and prohibitively expensive (or irreversible) after data exists:

- **DAR-01** — the FR-062 version dimension must be in the `metric_value` PK before the first partition is created.
- **DAR-02** — one read-model architecture and a complete table catalog before Phase 0/2 implementation; two contract documents currently disagree on the core dashboard path.
- **DAR-03** — PII rules for append-only/immutable stores before the Phase 0 audit log ships; un-pseudonymized PII in never-edited stores forecloses FR-142.

DAR-04..DAR-10, DAR-12, DAR-13 by Sprint 3 / next design iteration. DAR-11 is a consciously accepted ceiling with named triggers.

## 10. Inviolable principles

1. **PostgreSQL is the sole system of record**; Kafka topics are transport with bounded retention and are never replayed to reconstruct primary state (EventModel §11, ADR-003).
2. **Every tenant-scoped table has `tenant_id` + forced RLS bound via `SET LOCAL app.tenant_id`**; no-RLS tables are an enumerated, signed-off list; maintenance bypass runs only as `eip_maintenance`, audited (DatabasePlan §2, §5; FR-128).
3. **All event publication goes through the transactional outbox** — no component ever writes DB and Kafka independently (EventModel §9).
4. **Append-only tables are never UPDATEd or DELETEd by application code** (`audit_event`, `work_item_transition`, `metric_value`); correction = new rows/new version, erasure = pseudonym-mapping removal or crypto-shred, never row edits (DatabasePlan §1; FR-062; DAR-03 design).
5. **Metric history is immutable per definition version**; definition changes create a new series version (FR-062).
6. **Migrations are one-way, expand–contract, Flyway-only**; no backfill >10⁶ rows inside a migration (DatabasePlan §7; FR-131).
7. **No index without a named query pattern and EXPLAIN evidence**; partitioned-table queries must prune on the partition key (DatabasePlan §4/§6; PerformanceChecklist).
8. **Derived stores (read models, MVs, RAG index, caches) must always be rebuildable from canonical data** — never backed up as truth, never the only copy of anything (DataFlow §9; ADR-011).
9. **Vector retrieval is tenant-filtered before similarity ranking, with RLS as backstop**; the tenant filter is injected by the SPI, never caller-supplied (DatabasePlan §11; RAGArchitecture §7).
10. **No plaintext secrets or credential material in any table, event, or log**; secrets live only in `core.secret` under envelope encryption (DomainModel §14 rule 4; FR-113).
