# ADR-026: Deployment-level claim mapping, resource-level team scope, and tenant-editable role-permission overrides

- **Status:** Proposed (implementation-driven; closes the remainder of the DEBT-012 residual — deployment-level OIDC claim-name overrides, SecurityModel §4 layer 2 resource-level team scope, and tenant-editable persona role-permission overrides)
- **Approver:** pending R-SA review (no schema falls under DatabasePlan §2's no-RLS exception list this time — `core.tenant_role_permission_override` is uniformly tenant-scoped RLS — so the governance gap ADR-025 flagged does not recur here)
- **Affected anchors/modules:** [SecurityModel §3/§4](../architecture/SecurityModel.md); `eip-app` (`security.{EipPrincipal,EipPrincipalFilter,EipOidcClaimProperties,EipTenantClaimValidator,SecurityConfig,ServiceTokenAuthenticationFilter}`, `tenant.OidcTenantResolver`, `application.{TeamScopeFilter,TeamScoped*Query,EffectivePermissionResolver,RolePermissionOverrideService}`, `persistence.{RolePermissionOverrideStore,RolePermissionOverrideRepository}`, `api.AdminRolePermissionController`); `eip-tenancy` (`rbac.{Role,Permission}` read-only — unchanged). CC-4 (schema/migration), CC-1-adjacent (touches the RBAC enforcement path, though the `Role`/`Permission` catalog itself is untouched).

## Context

The DEBT-012 register entry's "still open" list named three residual gaps after the OIDC/RBAC and service-token waves: (1) no per-tenant claim-mapping config — `eip_tenant`/`realm_access.roles` were fixed string literals; (2) no resource-level scope checks — SecurityModel §4 layer 2's own example ("an ENGINEERING_MANAGER on Team A cannot read Team B's delivery-risk detail") was undeliverable, since tenant-wide RLS was the only isolation boundary; (3) no seeded-persona role editing — the ten `Role`→permission mappings were fixed Java, not per-tenant editable. This ADR records the design for all three.

## Decision 1 — deployment-level (not per-tenant) claim-name overrides

`EipOidcClaimProperties` (`eip.security.oidc.tenant-claim`/`roles-claim`, defaults `eip_tenant`/`realm_access.roles`) replaces the hardcoded claim-name constants in `EipTenantClaimValidator`, `EipPrincipalFilter`, `SecurityConfig`, and `OidcTenantResolver`.

**Genuinely per-tenant claim mapping is out of scope, and here is why:** resolving a request's tenant-specific configuration requires knowing the tenant BEFORE the claim carrying that tenant's identity has been read — the OIDC tenant claim is the only pre-authentication signal this platform has for "which tenant is this," and using it to decide "which claim-mapping config to consult before trusting the tenant claim" is circular. Two structural ways out exist and both are rejected for v0.1: (a) one OIDC client/issuer per tenant, so the issuer URI itself selects the mapping — a deployment-topology change (multi-issuer resource server), not a property, and out of scope for this task's write-set; (b) trusting an unauthenticated hint (a header, a path segment) to pick the mapping before the token is validated — this reopens exactly the spoofable-tenant-selection hole `OidcTenantResolver`'s javadoc already documents `X-EIP-Tenant` as inadmissible for. Since one deployment of this platform has exactly one enterprise IdP realm in v0.1 (SecurityModel §3), a deployment-level override is the honest scope: it solves "our IdP names the roles claim differently than Keycloak's default," not "each of our tenants' IdPs names it differently." `roles-claim` is a dot-separated path walked through nested claim maps (`EipPrincipalFilter#extractRoleNames`), generalizing past Keycloak's two-segment `realm_access.roles` default to one-segment flat claims and deeper client-role paths like `resource_access.<client>.roles`.

## Decision 2 — resource-level team scope, gated to manager-scope roles

`EipPrincipal` gains `scopedTeamIds` (default empty = unrestricted, so every existing caller's behavior is byte-for-byte unchanged). `EipPrincipalFilter` resolves it from a new `eip_teams` JWT claim (JSON array of team-id strings) — **but only for a manager-scope role holder** (`ENGINEERING_MANAGER`/`TEAM_LEAD`/`RELEASE_MANAGER`, SecurityModel §4's own naming for that group). A non-manager-scope caller presenting the claim anyway has it ignored (ends up unrestricted), mirroring how an unknown role name is ignored rather than trusted — the claim only ever narrows a role SecurityModel §4 already describes as team/project-scoped; it is not a general-purpose scoping mechanism for every role.

**Enforcement point:** SecurityModel §4 layer 2's example is friction-detail-specific, and the actual composition of `TeamFrictionView`/`TeamTrendView`/`TeamInFlightView`/`TeamRecommendationsView` lists lives in `eip-analytics`' application services (`FrictionSummaryService`, `TrendService`, `InFlightService`, `RecommendationService`), not in `eip-app` as this task's write-set brief assumed (`eip-app`'s controllers — `FrictionController`/`MetricsController`/`InsightsController` — inject those query-port interfaces directly, with no intermediate `eip-app`-owned composing service to modify). Since `eip-analytics` is outside this change's write-set and touching it was explicitly out of bounds, enforcement is instead a set of `@Primary`-decorated `TeamScoped*Query` beans in `eip-app.application` that wrap each real query-port bean (resolved by `@Qualifier("<beanName>")`, never by importing the concrete `eip-analytics` class — keeping `ArchitectureRulesTest#eip_app_owns_no_pipeline_business_logic` green) and filter the returned list by `TeamScopeFilter.restrictedTo` before the response ever reaches the controller. Spring's bean-primary resolution means every existing controller receives the decorated bean automatically, with **zero changes to any existing controller file** — satisfying the "new controller only" `api/**` constraint while still filtering at the composition layer, just one layer further out (decorating the query port itself) than assumed. `FrictionSummaryView.teamsReporting` (a derived cross-team count) is recomputed from the FILTERED list, not left at its true tenant-wide value, so a scoped caller never learns how many teams exist beyond their own. The single-team drill-down (`GET /friction/teams/{id}/evidence` — SecurityModel §4's own illustrative example) is guarded directly (`TeamScopeFilter.requireInScope`, 403 `PermissionDeniedException`) rather than silently filtered, since there is nothing to filter — a request naming an out-of-scope team is refused outright.

**Service tokens:** SecurityModel §3 ties team scope to manager-scope roles that only ever authenticate via OIDC in practice today; a service token's `EipPrincipal` construction (`ServiceTokenAuthenticationFilter`) always resolves `scopedTeamIds` to empty. Adding a `scoped_team_ids` column and threading it through would need a new field on `ServiceTokenController`'s creation request — an EXISTING controller, outside this change's "new controller only" boundary on `com.eip.app.api`. Wiring the column with no way to ever populate it would be dead schema, so it was skipped rather than half-built; this is flagged as a deliberate, documented gap, not a silent omission.

**Write-set note:** `com.eip.app.tenant.OidcTenantResolver` was touched despite living outside this change's declared `com.eip.app.security`/`com.eip.app.application` write-set, because it independently hardcoded the exact tenant-claim name `EipOidcClaimProperties` now makes configurable — leaving it untouched would silently break RLS tenant binding under a non-default `tenant-claim` override while `EipTenantClaimValidator`/`EipPrincipalFilter` correctly read the new name, an inconsistency judged worse than the narrow boundary exception. No other file outside the declared write-set was modified.

## Decision 3 — tenant-editable role-permission overrides as a delta table, not a full-list overwrite

`core.tenant_role_permission_override` (`tenant_id, role, permission, granted`, PK `(tenant_id, role, permission)`, standard RLS) stores per-tenant deltas on top of `Role.permissions()` — which remains the fixed, `RbacMatrixTest`-verified default matrix. Effective permissions = defaults with every `granted=false` row's permission removed and every `granted=true` row's permission added. `RolePermissionOverrideService` (implementing the new `EffectivePermissionResolver` seam) computes this with a single `WHERE role IN (:roles)` query against the PK — covering every role a principal holds in one indexed lookup, not one query per role or per permission — and `EipPrincipalFilter` calls it (via an explicit-tenant `TenantTransactionRunner.read`, since it must run in both `header` and `oidc` mode BEFORE `TenantContextHolder` is necessarily bound) instead of calling `Role.permissions()` directly.

**Rejected: reusing `core.role`** (V1, a tenant-scoped `permissions text[]` column already in the schema). Nothing in this codebase reads or writes `core.role` today — the actual RBAC implementation evolved as the fixed Java `Role`/`Permission` enum pair, leaving `core.role` unused dead schema. Repurposing it was rejected for two reasons: it is riskier to load-bear a forgotten table than add a new, narrowly-shaped one; and its shape is a full permission-LIST overwrite, which would force every write to already know (and stay in sync with) the CURRENT default set — silently drifting every time `Role.permissions()` changes in a future release. A delta table never goes stale that way: an empty table is always exactly "every role behaves as its Java default," the safest possible failure mode.

**`PUT` semantics:** upsert-merge over the given entries, not a full replace — entries not named in a request are left untouched. A full-replace `PUT` risks a caller accidentally clearing every OTHER already-configured override for a role by omission when they only meant to toggle one permission; this is a deliberate, documented REST-semantics choice, flagged as a deviation from a literal `PUT`-replaces-the-collection reading.

**Self-lockout guard:** a batch that would set `granted=false` for `(TENANT_ADMIN, USER_MANAGE)` is rejected atomically (`ValidationException`, no partial application) — the one permission every tenant needs at least one holder of to administer roles/overrides at all. `USER_MANAGE` (wire id `user.manage`) is the exact permission `ServiceTokenController`'s admin endpoints already gate on for the same reason (SecurityModel §4: `TENANT_ADMIN`/`PLATFORM_ADMIN` hold it, every lesser role does not).

**API:** `GET`/`PUT /api/v1/admin/roles/{role}/permissions`, `USER_MANAGE`-gated (`AdminRolePermissionController`, a genuinely new controller — no existing `api/**` file was modified for this decision).

## Consequences

- **Positive:** every existing principal's behavior is unchanged by default (empty overrides, empty scope, default claim names); the decorator approach for team scope required zero changes to `eip-analytics` or any existing `eip-app` controller; the override table's delta shape cannot drift from the Java default matrix the way a full-list copy would.
- **Negative:** `EipPrincipalFilter` now performs one additional indexed DB query per authenticated request (both `header` and `oidc` modes) to resolve effective permissions — a real, accepted per-request cost, already precedented by `ServiceTokenAuthenticationFilter`'s own per-request hash lookup on the same filter chain. The team-scope decorators add a small in-memory filter pass over already-fetched rows (no extra query).
- **Deferred:** service-token `scoped_team_ids` (Decision 2); genuinely per-tenant claim mapping (Decision 1) — both explicitly out of scope, not silently dropped.
- **Governance:** `core.tenant_role_permission_override` is a standard RLS-backed, uniformly tenant-scoped table — it does NOT extend DatabasePlan §2's no-RLS exception list, so the R-SA+R-DBA sign-off gate ADR-025 flagged for `core.service_token` does not apply here; ordinary schema review applies.

## Alternatives rejected

- **Header-based tenant hint to select per-tenant claim config** (Decision 1) — rejected: reintroduces a spoofable pre-authentication tenant signal, the exact hole `X-EIP-Tenant` is already documented as inadmissible for in `oidc` mode.
- **Filtering `Team*View` lists inside the existing controllers** (Decision 2) — rejected: `api/**`'s write-set constraint for this change is "new controller only"; filtering there would require editing `FrictionController`/`MetricsController`/`InsightsController`.
- **A full permission-list override column (mirroring `core.role`)** (Decision 3) — rejected: see "Rejected: reusing `core.role`" above.
- **`PUT` as a strict full replace of a role's override set** (Decision 3) — rejected: a single-permission toggle should not risk silently clearing unrelated overrides; documented as upsert-merge instead.
