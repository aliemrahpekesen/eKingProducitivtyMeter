# ADR-025: Service-token schema, hashing scheme, and hybrid-table RLS treatment

- **Status:** Proposed (implementation-driven; formal R-SA + R-DBA sign-off on the no-RLS addition is outstanding — see Consequences)
- **Approver:** pending (DatabasePlan.md §2 requires R-SA + R-DBA sign-off for any addition to the enumerated no-RLS exception list; this ADR records the engineering rationale for that request, not the sign-off itself)
- **Affected anchors/modules:** [SecurityModel §3](../architecture/SecurityModel.md), [DatabasePlan §2](../engineering/DatabasePlan.md); `eip-tenancy` (`rbac.ServiceTokenGenerator`), `eip-app` (`security.ServiceTokenAuthenticationFilter`, `persistence.ServiceTokenRepository`, `application.ServiceTokenService`, `api.ServiceTokenController`); CC-4 (schema/migration).

## Context

SecurityModel §3 specifies service tokens (`eipt_...`) as a third, mode-independent authentication path alongside `header`/`oidc`, tracked as the first part of the DEBT-012 residual ("no service-token auth path"). Implementing it requires a new table, `core.service_token`, whose rows are **not uniformly tenant-scoped**: a token created by a `TENANT_ADMIN` is bound to that tenant (`tenant_id` set); a token created by `PLATFORM_ADMIN` is platform-scoped (`tenant_id NULL`), matching `core.tenant`'s own scope. Every other table in the DatabasePlan §2 catalog is either uniformly tenant-scoped (RLS via the standard `tenant_isolation` policy) or uniformly platform-scoped (the enumerated no-RLS exception: `core.tenant`, `core.worker_heartbeat`, `analytics.analytics_watermark`, `quartz.qrtz_*`). `core.service_token` is neither — it is genuinely both, in the same relation.

A second, structural constraint: the token's own **authentication lookup** (`ServiceTokenAuthenticationFilter` hashing the presented bearer value and finding it by `token_hash`) necessarily runs **before** any tenant is known — discovering the token's bound tenant (or platform scope) is the entire point of the lookup. A `tenant_isolation` policy of the standard shape (`tenant_id = current_setting('app.tenant_id')::uuid`) would either error (the GUC is unset at that point in the request) or hide the very row the lookup exists to find.

## Decision

1. **No RLS on `core.service_token`**, added to DatabasePlan §2's enumerated no-RLS exception list alongside `core.tenant`. The application layer is the sole enforcement point: `ServiceTokenRepository` filters explicitly (`tenant_id = :tenantId` for a tenant-scoped listing/revocation, `tenant_id IS NULL` for a platform-scoped one, unscoped-by-hash for the auth lookup); `ServiceTokenService` checks the caller holds `PLATFORM_ADMIN` before ever calling a platform-scoped repository method. This mirrors `core.tenant`'s existing "no RLS, application enforces" precedent rather than inventing a new RLS shape for a table that cannot fit the uniform per-tenant policy.
2. **Token format:** `"eipt_" + 32 URL-safe base64 characters` from `java.security.SecureRandom` (192 bits of entropy before encoding overhead). The first 8 characters after the prefix are retained in the clear as `token_prefix` for admin-panel identification (not enough to reconstruct the token). The full raw token is never stored; only its SHA-256 hex digest (`token_hash`) is, looked up by exact match on presentation. This is intentionally the same one-way, re-hash-and-compare pattern as password hashing, not the reversible envelope encryption `SecretsService`/`core.secret` use (SecurityModel §6) — a service token is validated by re-derivation, never revealed back, so envelope encryption (designed for values that must be read back in plaintext) is the wrong primitive.
3. **Role/permission-subset representation:** `role` stores the `Role` enum's name verbatim (`CHECK` against the current ten names, expand-only on new roles); `permission_subset` stores `Permission` enum names (nullable/empty meaning "all of the role's permissions"), validated at creation to be a subset of the role's actual permission set.

## Consequences

- **Positive:** the auth-lookup path works correctly with no tenant context bound; a hybrid table gets a coherent, precedented treatment instead of a bespoke RLS predicate; the token/hash scheme reuses a well-understood one-way pattern already familiar from password storage, distinct from (and not confusable with) the reversible secrets-encryption path.
- **Negative:** `core.service_token` has **no RLS backstop at all** — unlike every genuinely tenant-scoped table, a bug in `ServiceTokenRepository`'s explicit `WHERE tenant_id = ...` filtering would not be caught by a second, independent enforcement layer. This is the same residual risk `core.tenant` already carries, applied to a table with much higher row count and a hotter (per-request) access path. Mitigation: `ServiceTokenRepository` is a small, single-purpose class with unit + integration test coverage over every listing/revocation path (`ServiceTokenRepositoryIntegrationTest`), and no other code is permitted to query `core.service_token` directly.
- **Governance gap:** DatabasePlan §2 states any addition to the enumerated no-RLS exception list "requires R-SA + R-DBA sign-off." This ADR is filed as the engineering record of the decision and its rationale, but that sign-off has not been separately obtained in this session — flagged explicitly in the implementing task's final report rather than assumed. If a reviewer with that authority prefers the alternative (a conditional RLS policy using `current_setting('app.tenant_id', true)` with `missing_ok = true` to degrade to no-op when unbound, tightening WITH CHECK to prevent a bound tenant session from ever inserting a platform-scoped row), that is a viable follow-up hardening and does not require a schema change to adopt — only a new policy in `R__rls_policies.sql`.

## Alternatives rejected

- **RLS with `tenant_id IS NULL OR tenant_id = current_setting('app.tenant_id')::uuid`** — rejected as the primary design: this predicate still errors when no GUC is bound at all (the auth-lookup path, which runs pre-tenant-context), and an unconditional `tenant_id IS NULL` disjunct would let any tenant-bound session see every platform-scoped token's metadata, a real (if narrow) disclosure. A conditional variant using `current_setting(..., true)` avoids the error but was set aside for this pass to avoid inventing a new, unprecedented policy shape without the governance sign-off DatabasePlan §2 calls for; noted above as a follow-up option.
- **Splitting into two tables (`core.service_token` tenant-scoped + `core.platform_service_token` platform-scoped)** — rejected: doubles the schema and every query path (auth lookup would need to check two tables on every request) for a distinction the application layer already needs to make explicitly regardless.
- **Reversible envelope encryption (matching `core.secret`)** — rejected: service tokens are never read back, only re-derived and compared; a one-way hash is the correct primitive and avoids holding a KMS-unwrappable copy of a bearer credential at rest.
